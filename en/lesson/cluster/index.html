Anatomy of a cluster

Who decides where everything runs? A guided tour of the cluster’s front office and kitchen.

10 minBeginner11 steps

▶ Open the interactive lesson

This is the text version. The interactive lesson has the animated diagram for each step.

You will learn

  • Know what a cluster and a node are
  • Tell the control plane apart from the nodes
  • Meet the API server, etcd, scheduler and controllers
  • Know what runs inside each node

Step by step

Step 1 · ConceptA cluster is a team of machines

A cluster is a group of computers working as if they were one. Each computer in the group is a node.

Your containers run inside pods (the next lesson covers them in detail), and the pods are spread across the nodes. You don’t care which machine each one is on: the cluster takes care of that.

Key idea: You no longer talk to servers one by one. You talk to the cluster, and it shares out the work.

kubectl get nodes

Step 2 · ConceptFront office and kitchen

Think of a restaurant. In the kitchen, cooks prepare the dishes. In the front office, someone takes the orders, writes everything down and decides who does what.

A cluster works the same way: the nodes are the kitchen, where applications actually run. The control plane is the front office: it doesn’t cook anything, it only makes decisions.

Good to know: With cloud services like EKS (Amazon), GKE (Google) and AKS (Microsoft), the provider runs the front office for you. You only see, and pay for, the nodes.

Step 3 · ConceptAPI server: the order counter

Every request to the cluster goes through a single counter: the API server. When you type a command in kubectl, the Kubernetes command-line tool, it sends a request to that counter.

The other components don’t talk to each other directly either: they all read and write through the counter. That way there’s one source of truth and one place to check permissions.

Key idea: kubectl is the menu you order from; the API server is the counter that takes the order, checks you’re allowed and writes it down.

kubectl get pods

Step 4 · Conceptetcd: the front office notebook

Everything the counter accepts is written in a notebook called etcd: which apps exist, how many copies of each, which settings. It is the cluster’s memory.

So it never loses notes, etcd keeps copies on 3 or 5 machines and only confirms a write once most of them agree. This is called consensus.

Watch out: If etcd is lost without a backup, the cluster forgets everything that should be running. Backing it up is a must for anyone running their own control plane.

Step 5 · ConceptScheduler: who assigns the shifts

A new pod has arrived and nobody said where it should run. The scheduler decides.

It works in two rounds. First it rules out the nodes that won’t do: no free memory, missing hardware, blocked by some rule. Then it scores the ones left and picks the best, like a manager giving the job to the least busy cook.

Good to know: The scheduler only decides and writes down the decision. The chosen node is what actually starts the pod.

kubectl get pods -o wide

Step 6 · ConceptControllers: the inspector who never sleeps

Controllers are a set of small inspectors. Each one watches one kind of thing and compares what should exist with what actually exists.

If the notebook says “I want 4 API pods” and only 2 exist, the inspector creates 2 more. If there were 5, it would delete 1. This loop of looking, comparing and fixing is called reconciliation.

Key idea: Desired different from actual: the controller acts. Desired equal to actual: nothing happens. The loop runs all the time, forever.

Step 7 · Conceptkubelet: the supervisor on each machine

Every node has a supervisor called the kubelet. It asks the API server which pods should run on its machine and makes sure they’re up.

It also runs health checks: every so often it “pokes” each container to see if it’s alive and answering. If one doesn’t answer, it restarts it.

Good to know: The green rings in the diagram are health checks: little “are you OK?” questions.

kubectl describe node node-1

Step 8 · ConceptContainer runtime: who starts containers

To start a container, the node needs the image, the recipe. It downloads the image from a registry: an image warehouse such as Docker Hub or your company’s own.

The heavy lifting of downloading and running is done by the container runtime, usually containerd. The kubelet just gives the order.

Watch out: Pulling a large image can take tens of seconds. Slim images make the cluster react faster.

Step 9 · ConceptEvery pod has its own address

Each pod gets its own IP address, like an internal phone extension. A pod can call another on any node without knowing which machine it’s on.

The cluster network builds that plumbing, with help from kube-proxy on each node. To you, it looks like all the pods are in the same room.

Key idea: Pod addresses change when a pod is recreated. In the Service lesson you’ll see how a fixed name solves that.

Step 10 · Trade-offTrade-off: what if the front office goes down?

The API server has stopped. Curiously, the store stays online: pods that were already running keep serving, because nodes don’t need the front office to do their work.

But nobody can change anything: you can’t update, scale or recover a pod that dies. That’s why, in production, the control plane runs as 3 copies.

Watch out: A control plane outage doesn’t take the app down right away, but it leaves the cluster with nobody to fix problems.

Step 11 · SummarySummary: who does what

The front office decides, the kitchen executes, and every conversation goes through the counter.

Good to know: If you use managed Kubernetes you’ll rarely touch the control plane. But knowing who does what helps a lot when tracking down problems.
