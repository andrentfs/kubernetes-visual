ConfigMaps, Secrets and SecurityContext

Taking settings and passwords out of the image, and running containers with as little power as possible.

12 minIntermediate11 steps

▶ Open the interactive lesson

This is the text version. The interactive lesson has the animated diagram for each step.

You will learn

  • Separate settings from the image with a ConfigMap
  • Choose between environment variable and file
  • Keep passwords in Secrets
  • Run containers without root
  • Block unsafe pods with Pod Security

Step by step

Step 1 · ProblemSettings stuck inside the image

The database address was written straight into the API code: DB_HOST=prod-db. To run the same API in staging, the team has to build another image.

One image per environment is slow and risky: the image you tested isn’t the one that goes to production.

Watch out: The rule for modern apps: the same image everywhere, only the settings change.

Step 2 · SolutionConfigMap: settings outside the image

A ConfigMap is a Kubernetes object that stores key-value pairs or whole config files, like DB_HOST=db.

Pods read the ConfigMap when they start. For another environment, just use another ConfigMap with the same name in another namespace; the image stays the same.

Key idea: ConfigMaps are for data that isn’t secret. Limit of 1 MiB per object.

kubectl create configmap loja-config --from-literal=DB_HOST=db

Step 3 · ConceptTwo ways to deliver: variable or file

As an environment variable: env with valueFrom.configMapKeyRef (one key) or envFrom (every key at once).

As a file: a configMap volume mounted in a folder, for example /etc/config. Each key becomes a file inside it.

Good to know: Use env for short values (ports, URLs) and a volume for whole files (nginx.conf, application.yaml).

Step 4 · Trade-offTrade-off: who sees the change?

You changed the ConfigMap. The pod that got it as a volume sees the new file within about a minute, on its own.

The pod that got it as an environment variable keeps the old value: variables are only read when the container starts. It needs a restart.

Watch out: Mounts using subPath don’t update on their own either. When in doubt, kubectl rollout restart.

kubectl rollout restart deployment/api

Step 5 · SolutionSecret: for passwords and keys

Passwords, tokens and certificates go in a Secret. It works almost like a ConfigMap: env or volume.

The difference is in the handling: RBAC can separate who reads Secrets, the kubelet keeps Secret volumes in memory (tmpfs) on the node, and they can be encrypted in etcd.

Watch out: By default the value is only base64. echo … | base64 -d shows the password. It isn’t encryption.

kubectl create secret generic db-cred --from-literal=password=s3nh4

Step 6 · ConceptKinds of Secret

Opaque is the generic one, for any key-value. kubernetes.io/tls holds a certificate and key (used by Ingress for HTTPS).

kubernetes.io/dockerconfigjson holds a private registry login. The pod uses that Secret in imagePullSecrets to be able to pull the image.

TypeHow to create
Opaquecreate secret generic
TLScreate secret tls
Registrycreate secret docker-registry
kubectl create secret tls loja-tls --cert=tls.crt --key=tls.key

Step 7 · ProblemA container running as root

By default, many images run as root (user 0). If someone breaks into the app through a flaw, they start with maximum power inside the container.

Combined with other mistakes (a node folder mounted, a privileged container), the attacker can reach the node itself.

Watch out: Root in the container is one step fewer between an app flaw and control of the machine.

Step 8 · SolutionSecurityContext: running with less power

The securityContext sets how the container runs. runAsNonRoot: true refuses to start as root; runAsUser: 1000 picks the user.

readOnlyRootFilesystem: true blocks writing to the container’s disk, and allowPrivilegeEscalation: false stops it from gaining more power after it starts.

Key idea: The securityContext can go on the pod (applies to all containers) or on each container (overrides the pod’s).

Step 9 · ConceptCapabilities: powers one by one

In Linux, root’s powers are split into capabilities: opening ports below 1024, changing the network, changing file owners…

The safest approach is capabilities.drop: ["ALL"] and add back only what’s needed, like add: ["NET_BIND_SERVICE"] to listen on port 80.

Good to know: privileged: true turns on every capability and nearly everything on the node. Avoid it, except for very specific system agents.

Step 10 · ConceptPod Security: the namespace’s doorman

So you don’t depend on every team remembering the securityContext, the Pod Security admission controller enforces rules per namespace.

With the label pod-security.kubernetes.io/enforce=restricted, the API server rejects pods that run as root, ask for privileges or don’t drop capabilities.

LevelWhat it requires
privilegedNothing, everything allowed
baselineBlocks the most dangerous
restrictedFull best practices
kubectl label ns loja pod-security.kubernetes.io/enforce=restricted

Step 11 · SummarySummary: pod configuration and security

The image is the same everywhere; what changes comes from ConfigMaps and Secrets, and the container runs with as little power as possible.

ResourceWhat for
ConfigMapOrdinary settings
SecretPasswords, tokens, certificates
securityContextUser, permissions, disk
