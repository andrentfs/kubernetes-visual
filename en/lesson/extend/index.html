Extensions: CRI, CNI, CSI, CRDs and Operators

Kubernetes is a platform: runtime, network and disk plugins, and new object types with their own controllers.

12 minIntermediate10 steps

You will learn

  • Know the CRI, CNI and CSI interfaces
  • Understand what a CRD is
  • Understand the Operator pattern
  • Install and explore operators

Step by step

Step 1 · ContextThree standard sockets

The kubelet doesn’t know how to run containers, wire networks or create disks on its own. It talks to plugins through three standard interfaces.

CRI for the container runtime, CNI for pod networking, CSI for storage. Any plugin that follows the interface fits.

Key idea: It’s like a wall socket: Kubernetes defines the shape, and each vendor makes its own plug.

Step 2 · ConceptCRI: the container runtime

Container Runtime Interface. The kubelet says “create this container” and the runtime does it: containerd and CRI-O are the most common.

On the node, crictl talks straight to the runtime over CRI: ps, logs, images, inspect. Handy when kubectl can’t help.

Good to know: Docker Engine doesn’t speak CRI directly; since 1.24 Kubernetes uses containerd or CRI-O.

crictl ps

Step 3 · ConceptCSI: disk drivers

Container Storage Interface. Each storage provider (EBS on AWS, Persistent Disk on GCP, Ceph…) publishes a CSI driver.

The StorageClass names the driver in its provisioner field, and the driver creates, attaches and grows the disks.

kubectl get csidrivers

Step 4 · ConceptCNI: networking, again

Container Network Interface, which you met in the networking lesson. When a pod is born, the runtime calls the CNI plugin to give it an IP and wire it to the network.

The config lives in /etc/cni/net.d; the binaries in /opt/cni/bin.

ls /etc/cni/net.d

Step 5 · ConceptCRD: teaching Kubernetes a new type

A CustomResourceDefinition adds a new type to the API, like Database. Once applied, the API server accepts objects of that type and kubectl knows about them.

The CRD defines the name, the group (like loja.com/v1) and the fields’ schema.

kubectl apply -f database-crd.yaml

Step 6 · ConceptAn object of the new type

Now you create a Database called loja-db with replicas: 3 and storage: 20Gi. It’s stored in etcd like any other object.

But on its own, nothing happens: no pod is born. The CRD only taught the format; something that knows how to act is missing.

Watch out: A CRD without a controller is just a stored form.

kubectl get databases

Step 7 · ConceptOperator: the automated expert

An Operator is a controller that watches objects of the new type and does the work: it sees loja-db and creates a StatefulSet, Services, PVCs, sets up replicas and backups.

It’s the same reconciliation loop as the built-in controllers, with an expert’s knowledge (a DBA, for example) written in code.

Key idea: CRD + controller = Operator. You declare “I want a database with 3 replicas” and it handles the rest.

Step 8 · ConceptInstalling an operator

Operators usually come as Helm charts or ready-made manifests, which install the CRDs and the operator pod together.

Common examples: cert-manager (TLS certificates), Prometheus Operator (monitoring), database operators like CloudNativePG.

helm install cert-manager jetstack/cert-manager -n cert-manager --create-namespace --set crds.enabled=true

Step 9 · ConceptExploring CRDs in the cluster

kubectl get crd lists the new types. kubectl api-resources shows every type, built-in and custom, with short name and group.

kubectl explain also works with CRDs that have a schema: kubectl explain certificate.spec.

kubectl get crd | grep cert-manager

Step 10 · SummarySummary: how Kubernetes grows

Standard interfaces let you swap runtime, network and disk. CRDs and Operators let the API itself grow.
