Cluster security: CIS, API, tokens, metadata and TLS

Closing the doors a default install leaves open: CIS benchmark, API access, tokens, cloud metadata, TLS and binaries.

You will learn

  • See the cluster’s attack surface

  • Edit the kube-apiserver without losing the cluster

Step by step

Step 1 · ContextWhere a cluster can be attacked

A freshly installed cluster has several entry points: the API server (6443), etcd (2379), the kubelet on each node (10250) and, in the cloud, the machine’s metadata service (169.254.169.254).

This is exactly what the CKS tests: review each of these entry points and leave open only what is needed, always with authentication.

Key idea: Kubernetes security comes in layers: control plane, nodes, network, images and what runs inside the containers.

Step 2 · Conceptkube-bench: the CIS Benchmark, automated

The CIS Kubernetes Benchmark is a list of recommendations for the control plane, etcd, the nodes and policies. kube-bench runs those checks and marks each item as PASS, FAIL, WARN or INFO.

kube-bench run --targets master checks the control plane; --targets node checks the nodes. For each FAIL it shows the suggested fix (remediation).

Watch out: Item numbers change between benchmark versions. In the exam, look up the item the task names and follow the fix kube-bench itself shows.

kube-bench run --targets master

Step 3 · SolutionFixing a failed item

Almost every fix is a flag in a static pod manifest under /etc/kubernetes/manifests, or a field in the kubelet config (/var/lib/kubelet/config.yaml, followed by systemctl restart kubelet).

A common example: --profiling=false on the kube-apiserver. When you save the manifest, the kubelet recreates the pod by itself. Run kube-bench again to see the PASS.

vi /etc/kubernetes/manifests/kube-apiserver.yaml

Step 4 · ProblemWhen the edit takes the API down

One typo in the manifest and the kube-apiserver doesn’t start: kubectl stops answering with connection refused.

Without the API, investigate on the node: crictl ps -a shows the container that exited, and the logs are in /var/log/pods or in crictl logs <id>.

Watch out: Before editing, copy the manifest outside the folder (to /root, for example). The kubelet reads the files in that folder, and a backup left there can become a second pod.

crictl ps -a | grep kube-apiserver

Step 5 · ConceptWho can talk to the API server

Requests with no credentials become the user system:anonymous. Check that no RoleBinding or ClusterRoleBinding gives permissions to system:anonymous or to the system:unauthenticated group.

On the kube-apiserver, --authorization-mode=Node,RBAC and the NodeRestriction admission plugin make each kubelet touch only its own Node and its own pods.

Key idea: The kubelet has an API too (port 10250). In its config: authentication.anonymous.enabled: false and authorization.mode: Webhook.

Step 6 · SolutionServiceAccounts without unneeded tokens

By default, every pod gets its ServiceAccount token mounted at /var/run/secrets/kubernetes.io/serviceaccount. If the app never talks to the API, that token only helps an attacker.

Turn it off with automountServiceAccountToken: false on the ServiceAccount or the pod. And create one ServiceAccount per app, with only the permissions it uses.

kubectl patch sa default -n loja -p '{"automountServiceAccountToken":false}'

Step 7 · ProblemThe cloud metadata endpoint

On AWS, GCP and Azure, any process on the machine can query 169.254.169.254 and get instance data, sometimes even temporary cloud credentials.

A compromised pod can reach that address too, because its traffic leaves through the node.

Watch out: With those credentials, the attacker leaves the cluster and starts acting in the cloud account.

kubectl exec app -- curl -s 169.254.169.254

Step 8 · SolutionBlocking metadata with a NetworkPolicy

An egress NetworkPolicy allows ipBlock 0.0.0.0/0 with except: 169.254.169.254/32. Everything else stays reachable; only the metadata endpoint is left out.

Exempt only the pods that really need metadata, such as the cloud provider’s own agents.

kubectl apply -f deny-metadata.yaml

Step 9 · SolutionIngress with TLS

The certificate and key live in a Secret of type kubernetes.io/tls: kubectl create secret tls loja-tls --cert=tls.crt --key=tls.key.

In the Ingress, spec.tls lists the hosts and the secretName. The controller then serves HTTPS with that certificate.

Watch out: The host in spec.tls must match the rules and the certificate. If it doesn’t, many controllers serve a default certificate.

kubectl create secret tls loja-tls --cert=tls.crt --key=tls.key

Step 10 · ConceptVerifying platform binaries

Before installing or upgrading, check that kubelet, kubeadm and kubectl are the official ones. The project publishes the hashes: each release’s CHANGELOG lists the SHA512 of the packages, and dl.k8s.io has a hash file next to each binary.

Compute it with sha512sum (or sha256sum) and compare with the value published for your version and architecture. Different value: don’t use it.

sha512sum /usr/bin/kubelet
