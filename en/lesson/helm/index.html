Helm and Kustomize

Installing and reusing whole applications without copying YAML for every environment.

13 minIntermediate10 steps

You will learn

  • Understand the problem with copying YAML
  • Install a chart with Helm
  • Customise with values
  • Upgrade and roll back with Helm
  • Build a base and overlays with Kustomize

Step by step

Step 1 · ProblemOne YAML per environment

The store has dev, staging and production. The team keeps three copies of the manifests, changing replica counts, image and domain by hand.

A fix made in production and forgotten in dev is just a matter of time. And installing something ready-made, like a full NGINX, would mean writing dozens of files.

Watch out: Copied YAML is debt: every change has to be repeated everywhere.

Step 2 · ConceptHelm: the package manager

Helm packages an application into a chart: YAML templates (templates/) with variables, and a values.yaml file with the default values.

Charts live in repositories, like an operating system’s packages. helm repo add registers a repository and helm search repo finds charts.

Key idea: The chart is the recipe; a release is each installation of it in the cluster, with its own name.

Step 3 · Solutionhelm install

helm install loja bitnami/nginx -n loja installs the chart with the release name “loja”. Helm renders the YAML, applies it to the cluster and stores revision 1.

helm list -A shows every release in every namespace, with chart version and status.

helm install loja bitnami/nginx -n loja --create-namespace

Step 4 · ConceptCustomising with values

You change the default values without touching the chart: --set replicaCount=3 on the command line, or -f values-prod.yaml with several values together.

helm show values bitnami/nginx lists every value the chart accepts.

Good to know: One values file per environment replaces the three YAML copies: the chart stays the same.

helm upgrade loja bitnami/nginx --set replicaCount=3 -f values-prod.yaml

Step 5 · Concepthelm upgrade and rollback

helm upgrade applies new values or a new chart version and creates a new revision. helm history shows every revision.

Went wrong? helm rollback loja 1 goes back to revision 1. Helm reapplies what was there in that revision.

helm history loja && helm rollback loja 1

Step 6 · ConceptLook before you apply

helm template renders the YAML without installing anything. Great for reviewing or saving to a file.

helm uninstall loja removes everything the release created. --dry-run shows what install or upgrade would do.

helm template loja bitnami/nginx > out.yaml

Step 7 · ConceptKustomize: base and overlays

Kustomize takes another route: no templates. You write normal YAML in a base/ folder and create overlays/ for each environment, describing only the differences.

It’s already built into kubectl: nothing to install.

Key idea: Helm uses variables in templates. Kustomize applies tweaks on top of plain YAML.

Step 8 · ConceptThe kustomization.yaml file

Each folder has a kustomization.yaml. In the base, it lists the files (resources). In the overlay, it points to the base and adds tweaks.

Common tweaks: namePrefix (prod-), namespace, images (swap the image tag), replicas and patches (bits of YAML that override fields).

Step 9 · Solutionkubectl apply -k

kubectl apply -k overlays/prod merges the base with the overlay’s tweaks and applies it to the cluster. kubectl kustomize overlays/prod just shows the result.

The production pods get the prod- prefix and the image and replica count set in the overlay.

kubectl apply -k overlays/prod

Step 10 · SummarySummary: Helm or Kustomize?

Use Helm to install third-party software and packages with many options. Use Kustomize to vary your own manifests per environment.
