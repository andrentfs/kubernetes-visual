Container images

How an image is built in layers, published, and kept small and safe.

Step by step

Step 1 · ContextAn image is a stack of layers

An image isn’t a single file: it’s a stack of layers, one on top of the other. Each Dockerfile instruction creates a layer.

The first is the base (like node:22, which already includes Node.js); then come your files and commands.

Step 2 · ConceptThe Dockerfile, line by line

FROM picks the base image. WORKDIR sets the working folder. COPY brings files from your computer. RUN executes a command during the build, like installing dependencies.

CMD (or ENTRYPOINT) says what to run when the container starts. docker build -t loja/api:1.0 . puts it all into an image with a name and tag.

Good to know: Tools like podman and buildah use the same Dockerfile, without needing Docker.

docker build -t loja/api:1.0 .

Step 3 · ConceptCache: only redo what changed

On rebuild, unchanged layers come from the cache. If only the code changed, only the last layer (COPY . .) is redone: the build takes seconds.

That’s why order matters: what rarely changes (dependencies) goes on top; what always changes (code), last.

Step 4 · ProblemWrong order, slow build

If COPY . . comes before RUN npm ci, any code change invalidates the cache from there down. Dependencies are downloaded again on every build.

Copy only package.json first, install, then copy the rest.

Watch out: A changed layer invalidates every layer after it.

Step 5 · SolutionPublishing to the registry

docker push sends the image to a registry (Docker Hub, GHCR, ECR, Harbor). Cluster nodes pull from there when a pod needs it.

The full name includes the registry: registry.loja.com/api:1.0. Without an address, the default is Docker Hub.

docker push registry.loja.com/api:1.0

Step 6 · ConceptMulti-stage: build big, ship small

Compiling needs heavy tools; running doesn’t. A multi-stage Dockerfile has several FROMs: the first stage compiles, the last copies only the result (COPY --from=build).

The final image is tens of MB instead of hundreds: it pulls faster and gives an attacker less to work with.

Step 7 · Trade-offTrade-off: the danger of latest

latest is just a name; it doesn’t mean “the newest”, and it can point to different things at different times. Two nodes can run different versions under the same tag.

Use versioned tags (api:1.4.2) or, to be sure, the digest (api@sha256:…), which identifies the exact content.

Watch out: imagePullPolicy Always pulls every time; IfNotPresent uses what’s already on the node. With latest, the default is Always.

Step 8 · ConceptSafer images

Start from a minimal base (alpine, distroless). Add USER with an unprivileged user, so the container doesn’t run as root.

Scan the image with tools like Trivy before publishing, and rebuild when the base gets fixes.

Step 9 · SummarySummary: good images

Small, pinned to a version, no root, and with layers in the right order.
