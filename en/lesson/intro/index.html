Why Kubernetes?

From a store on a single server to a cluster that looks after itself: the story of why Kubernetes exists.

9 minBeginner11 steps

You will learn

  • Understand what a server and a request are
  • Know what a container is and why it exists
  • See why depending on one server is risky
  • Understand what an orchestrator like Kubernetes does

Step by step

Step 1 · ContextIt all starts with a server

You run an online store. It lives on a server: a computer with no screen that stays on 24 hours a day in a data center, waiting for visitors.

Every time someone opens a page, adds a product to the cart or pays, their phone sends a message to the server and gets an answer back. That message is called a request.

Key idea: A server is just a computer dedicated to answering requests. The more people use the store, the more requests per second it has to handle.

Step 2 · Problem“But it works on my machine!”

To put the store online, you copy the code to the server and install everything it needs: the programming language, libraries, settings.

But the server is not the same as your laptop. It has another version of the language and other libraries installed by other systems. The store breaks now and then, and nobody can explain why.

Watch out: Installing programs straight onto the server creates a mess that is hard to repeat: every machine ends up slightly different from the next.

Step 3 · SolutionContainer: the app’s lunchbox

The fix is to pack the store together with everything it needs, like a lunchbox that already comes with the food and the fork. That package is called a container.

First you build an image: the frozen recipe for the lunchbox (here, loja/app:1.0). Then any server can “heat up” that image and run a container identical to the one you tested.

Good to know: The name comes from shipping containers: the port doesn’t need to know what’s inside, only how to stack the box. The server doesn’t need to know what’s inside the container either.

docker run -d -p 80:8080 loja/app:1.0

Step 4 · ConceptSeveral containers on one server

With containers, you split the store into parts: the website (web), the API that does the calculations, the database (db) and a queue that sends emails without slowing everything else down.

Each container is isolated: it has its own files and doesn’t fight with its neighbours. And it’s light: it starts in seconds, because it shares the operating system with the server.

Key idea: A container is not a virtual machine. A virtual machine pretends to be a whole computer; a container is just an isolated program. That’s why dozens of them fit on one server.

Step 5 · ProblemThen the store goes viral

An influencer posts about your store and visits jump from 100 to 12,000. The server starts sweating: the CPU, the “brain” that does the maths, goes above 90%.

Requests queue up waiting their turn, pages get slow, and some give up halfway.

Watch out: This is what overload looks like: CPU near 100%, growing queues, slowness and, finally, errors.

Step 6 · Problem…and the server goes down

Under all that pressure the disk fills up and the server freezes. Every container goes down with it, because they all lived on the same machine. The store is offline.

Someone has to notice, log into the server, free up space and start everything again in the right order. Usually at 3 a.m., with the phone ringing.

Watch out: When one single piece can take the whole system down, it is a single point of failure. The cure is having more than one copy of everything.

Step 7 · SolutionThree servers instead of one

You rent two more servers and spread copies of the containers across them: two with the website and the API, one with the database and the queue.

Now the load is shared (CPU drops to about 45%) and, if one server goes down, there are others left to serve customers.

Good to know: Growing by adding machines, instead of swapping for a bigger one, is called horizontal scaling. It’s how almost every large system grows.

Step 8 · ProblemMore machines, more work

One night, server-1 dies. The copies on server-2 hold the fort but get overloaded, and nobody restarts the lost containers somewhere else.

New questions appear: which server should each container run on? Who restarts what went down? How do you change the version on 3 machines without taking the store offline?

Watch out: Doing this by hand, with scripts and notes, works for 3 servers. With 30 it becomes a full-time job, and human mistakes creep in.

Step 9 · ConceptA conductor for the orchestra

In an orchestra every musician knows how to play their instrument, but someone has to decide who plays when. That’s the conductor.

Kubernetes is the conductor for containers. It joins the servers into one group, called a cluster, and calls each server a node. A special part, the control plane, makes the decisions for you.

Good to know: Kubernetes was created by Google in 2014, inspired by an internal system called Borg, and today it’s open source. Many people write k8s: the 8 stands for the eight letters between the k and the s.

Step 10 · ConceptYou say what. It handles how.

Instead of giving step-by-step orders (“start this here, then that there”), you write a file describing how you want things to be: “I want 2 copies of the website, 2 of the API, 1 database”.

Kubernetes constantly compares that wish with reality. A copy is missing? It creates one. A server died? It starts the copies on another. This is called the desired state.

Key idea: Think of an air conditioner: you pick 22 °C and it turns itself on and off to keep that temperature. You declare the state; Kubernetes chases that state forever.

kubectl apply -f loja.yaml

Step 11 · SummarySummary: before and after Kubernetes

Kubernetes doesn’t make your code faster. It takes away the job of watching, starting, moving and updating containers across many machines.

Good to know: Kubernetes has a learning curve. For a small site on a single server it can be overkill. It shines when there are many containers and many machines.

Where it runsYou chooseThe cluster chooses
