Installing and maintaining the cluster with kubeadm

From zero to a working cluster: preparing the machines, kubeadm init and join, upgrades, etcd backup, high availability and certificates.

  • Prepare nodes for Kubernetes

Step by step

Step 1 · ContextPreparing the machines

Before Kubernetes, each machine needs a container runtime (containerd), the kubeadm, kubelet and kubectl packages, and a few Linux tweaks.

The classic tweaks: turn off swap, load the overlay and br_netfilter modules, and set net.ipv4.ip_forward=1. The kubelet keeps running, waiting for orders.

Watch out: kubeadm, kubelet and control plane versions must be compatible. Install the same minor version of all three.

Step 2 · Solutionkubeadm init: the control plane is born

On the first node, kubeadm init creates everything: the certificates in /etc/kubernetes/pki, the static pod manifests (etcd, API server, scheduler, controller-manager) and the admin.conf file.

At the end it prints two commands: how to copy admin.conf to ~/.kube/config and the kubeadm join the workers will use.

Good to know: --pod-network-cidr sets the pods’ IP range. It must match the network plugin you’re going to install.

kubeadm init --pod-network-cidr=10.244.0.0/16

Step 3 · ProblemNode NotReady and CoreDNS stuck

Right after init, the node shows NotReady and the CoreDNS pods stay Pending. It’s not an error: the network plugin (CNI) is missing.

Kubernetes doesn’t ship its own network. Without a CNI, pods get no IP and the node isn’t considered ready.

Step 4 · SolutionInstalling the network plugin

You apply a CNI, like Calico, Cilium or Flannel, usually with a single kubectl apply. It runs a pod on every node.

With the network ready, the node goes Ready and CoreDNS starts.

kubectl apply -f calico.yaml

Step 5 · Solutionkubeadm join: the workers arrive

On each worker, the kubeadm join command with the API server address, a token and the certificate hash brings the node into the cluster.

The token expires in 24 hours. To generate another full command: kubeadm token create --print-join-command.

kubeadm token create --print-join-command

Step 6 · Conceptkubeconfig and contexts

The ~/.kube/config file has three lists: clusters (addresses), users (credentials) and contexts (which user on which cluster and namespace).

kubectl config get-contexts lists them, use-context switches, and set-context --current --namespace=app changes the default namespace.

Watch out: In the exam, each task starts with a use-context command. Skipping it is the most common mistake.

kubectl config use-context prod

Step 7 · ConceptUpgrade: one minor version at a time

You can’t skip versions: from 1.35 you go to 1.36, then 1.37. Control plane first, then the workers.

On the control plane: upgrade the kubeadm package, run kubeadm upgrade plan to see the options and kubeadm upgrade apply v1.36.0.

kubeadm upgrade plan

Step 8 · SolutionUpgrading workers, one at a time

For each worker: kubectl drain to move the pods out, upgrade the kubeadm package, run kubeadm upgrade node, upgrade kubelet and kubectl, systemctl daemon-reload and restart kubelet.

Finally, kubectl uncordon puts the node back to work. On the control plane the same applies to its kubelet: drain, upgrade, restart, uncordon.

Key idea: The order that shows up in the exam: drain → kubeadm → kubeadm upgrade → kubelet/kubectl → restart → uncordon.

kubeadm upgrade apply v1.36.0

Step 9 · SolutionBacking up etcd

etcd holds the whole cluster. A snapshot saves everything to one file: etcdctl snapshot save /opt/backup.db.

etcdctl needs the address and the certificates: --endpoints=https://127.0.0.1:2379, --cacert, --cert and --key, which live in /etc/kubernetes/pki/etcd. The etcd manifest shows the paths.

Watch out: Without the three certificates, etcdctl fails with a connection error. Copy the paths from /etc/kubernetes/manifests/etcd.yaml.

ETCDCTL_API=3 etcdctl snapshot save /opt/backup.db

Step 10 · SolutionRestoring etcd

etcdctl snapshot restore creates a fresh data folder from the file, with --data-dir /var/lib/etcd-restore.

Then edit the etcd manifest so its hostPath volume points to the new folder. The kubelet restarts etcd with the restored data.

Good to know: In recent versions the restore can also be done with etcdutl. The idea is the same: a new folder, and point the manifest at it.

etcdctl snapshot restore /opt/backup.db --data-dir /var/lib/etcd-restore

Step 11 · ConceptA highly available control plane

With a single control plane, losing that machine leaves the cluster unmanaged. Production uses 3 (or 5) control planes behind a load balancer on port 6443.

etcd can be stacked (one on each control plane) or external, on machines of its own. Always an odd number, because of consensus.

Good to know: With kubeadm: init with --control-plane-endpoint pointing at the load balancer, and join --control-plane on the others.

Step 12 · ConceptCluster certificates

kubeadm creates certificates valid for 1 year. kubeadm certs check-expiration shows the dates and kubeadm certs renew all renews them; an upgrade also renews them.

To give a person access, they generate a key and a CertificateSigningRequest; an admin approves it with kubectl certificate approve.

Watch out: An expired certificate cuts off access to the cluster all at once. Monitor the dates.

kubeadm certs check-expiration

Prepare, init, CNI, join; then maintain: upgrade version by version, back up etcd and keep certificates current.
