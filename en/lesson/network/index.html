Cluster networking: CNI, Services and CoreDNS

How pods find each other: the network model, Service types, the cluster DNS and the Gateway API.

Step by step

Step 1 · ContextThe golden rule of the network

In Kubernetes, every pod gets its own IP, and any pod can talk to any other pod by IP, on any node, with no address translation (NAT).

It’s as if every pod were on the same local network, even when spread across different machines.

Key idea: Pods have IPs, everyone can reach everyone, no NAT. By default there’s no blocking either: that’s NetworkPolicy’s job.

Step 2 · ConceptCNI: who builds the network

Kubernetes defines the rule but doesn’t implement the network. A CNI plugin (Container Network Interface) does: Calico, Cilium, Flannel…

It runs on every node (a DaemonSet), gives each new pod an IP and creates the routes between nodes.

Good to know: The CNI config lives in /etc/cni/net.d and the binaries in /opt/cni/bin. That’s where to look if pods get no IP.

Step 3 · Conceptkube-proxy: the real Service

A Service IP is virtual: no network interface has that address. On every node, kube-proxy creates rules (iptables or IPVS) that swap the Service IP for a real pod’s IP.

That’s why the Service works from any node: the rules are on all of them.

Good to know: Some CNIs, like Cilium, can replace kube-proxy using eBPF.

Step 4 · ConceptClusterIP: inside the cluster only

The default type. The Service gets a virtual IP (like 10.96.0.20) and a DNS name, reachable only from inside the cluster.

port is the Service’s port; targetPort is the container’s port. They can differ: 80 on the Service, 8080 in the app.

Watch out: Anyone outside the cluster can’t reach a ClusterIP. For that, use NodePort, LoadBalancer, Ingress or Gateway.

kubectl expose deploy api --port=80 --target-port=8080

Step 5 · ConceptNodePort: a port on every node

A NodePort opens the same port (between 30000 and 32767) on every node. Anyone hitting any node on that port reaches the Service.

It includes a ClusterIP underneath. Good for tests and labs; in production it usually sits behind a load balancer.

kubectl expose deploy api --type=NodePort --port=80

Step 6 · ConceptLoadBalancer: the cloud’s balancer

On clouds like AWS, GCP and Azure, a LoadBalancer Service asks the provider for an external balancer with a public IP, which sends traffic to the nodes.

Underneath it creates a NodePort and a ClusterIP. On local clusters with no provider, the external IP stays <pending> until you install something like MetalLB.

Step 7 · ConceptEndpoints and headless Services

Behind every Service is a list of endpoints (today in EndpointSlices) with the IPs of the ready pods.

A headless Service (clusterIP: None) has no virtual IP: DNS returns the pod IPs directly. It’s used with StatefulSets, where each replica has its own name (db-0, db-1…).

Step 8 · ConceptCoreDNS: the cluster’s names

CoreDNS runs in kube-system and answers the cluster’s names. A Service becomes api.loja.svc.cluster.local.

In the same namespace, “api” is enough; from another namespace, “api.loja”. Each pod’s /etc/resolv.conf already points to CoreDNS.

FromName that works
Same namespaceapi
Other namespaceapi.loja
Full nameapi.loja.svc.cluster.local
kubectl run t --image=busybox --rm -it -- nslookup api.loja

Step 9 · ProblemWhen DNS fails

Pods getting timeouts or NXDOMAIN calling other services? Test with a temporary pod: kubectl run t --image=busybox --rm -it -- nslookup api.loja.

If even kubernetes.default doesn’t resolve, check the CoreDNS pods (kubectl -n kube-system get pods -l k8s-app=kube-dns), their logs and the coredns ConfigMap.

Watch out: If the name doesn’t resolve but the Service IP works, it’s DNS. If even the IP fails, it’s the Service or the network.

kubectl -n kube-system logs -l k8s-app=kube-dns

Step 10 · ConceptGateway API: Ingress’s successor

The Gateway API splits the entry point into roles. The GatewayClass says which implementation to use; the Gateway defines where to listen (port, domain, certificate); routes, like HTTPRoute, say which Service each path goes to.

That way the infrastructure team owns the Gateway and each app team creates its own routes.

Good to know: Ingress still exists and is on the exam too. The Gateway API is more expressive: weights for canary, headers, several protocols.

Step 11 · SummarySummary: how traffic reaches the pod

CNI gives pods IPs, kube-proxy implements Services, CoreDNS gives names, and Ingress or Gateway open the door to the outside.
