When a node goes down

What happens, minute by minute, when a cluster machine disappears, and why pods don’t move house right away.

12 minIntermediate12 steps

▶ Open the interactive lesson

This is the text version. The interactive lesson has the animated diagram for each step.

You will learn

  • Understand node heartbeats
  • Know how long until a node turns NotReady
  • Understand automatic taints and the 5-minute toleration
  • See why StatefulSets and volumes get stuck
  • Unblock things with the out-of-service taint

Step by step

Step 1 · ContextEvery node says it’s alive

The cluster has three nodes. The API runs 3 replicas, one per node, and the database (db-0, from a StatefulSet) runs on node-3 with its disk.

Each node’s kubelet sends an “I’m alive” to the API server every 10 seconds by renewing an object called a Lease. Inside the controller-manager, one controller watches these signals: the node lifecycle controller.

Key idea: Kubernetes can’t see the machines. It only knows a node is alive because the kubelet keeps reporting in.

Step 2 · Problem0 s: the machine goes dark

node-3’s power supply died. The machine is gone, along with the API replica and the database running on it.

But for the cluster nothing has changed yet: the node is still Ready and the pods are still Running in kubectl. The only difference is the silence: node-3’s reports stopped arriving.

Watch out: For the first seconds, kubectl shows Running for things that no longer exist. It shows the last known state, not the real one.

kubectl get nodes

Step 3 · Concept50 s: the node turns NotReady

The controller waits a while before getting suspicious: the node-monitor-grace-period, 50 seconds (it was 40 s up to version 1.31). With no report in that time, it marks node-3 as NotReady, with status Unknown.

At the same moment it marks node-3’s pods as not ready (Ready: False). That already removes them from the Services’ endpoints: from now on no client is sent to the dead node.

Key idea: The first effect of a dead node is on traffic, not pods: within ~50 s Services stop sending clients there.

Good to know: Between 0 and 50 s some requests still land on the dead node and fail. Retries in the client or the Ingress cover that gap.

kubectl get nodes

Step 4 · ConceptThe node gets a “closed” sign

Along with NotReady, the controller puts two taints on node-3: node.kubernetes.io/unreachable with the NoSchedule effect, and the same with the NoExecute effect.

A taint is a sign on the node’s door. NoSchedule means “don’t put new pods here”, so the scheduler ignores node-3. NoExecute means “whoever is here must leave”, but only after the time each pod tolerates.

Good to know: If the machine only lost its network, its containers keep running in there, unaware. That’s why Kubernetes is careful before recreating pods elsewhere.

kubectl describe node node-3

Step 5 · ConceptEvery pod tolerates 5 minutes

Every pod gets, without you asking, a toleration for these taints: tolerationSeconds: 300. It’s like saying “if my node disappears, I’ll wait 5 minutes before leaving”.

The reason: short network blips are common. If Kubernetes recreated everything at every hiccup, a rebooting switch would move half the cluster for nothing.

Key idea: Pods on the dead node are only evicted about 5 minutes after NotReady. All in all, the new replica shows up about 5 min 50 s after the crash.

Good to know: You can change it per pod: a toleration for node.kubernetes.io/unreachable with tolerationSeconds: 30 makes the pod switch nodes much faster. Good for stateless apps; risky for databases.

Step 6 · Solution5 min 50 s: the pods are evicted

Time’s up. The controller deletes node-3’s pods, which now show as Terminating.

The API’s ReplicaSet notices it only has 2 real replicas and creates a new one. The scheduler picks node-1, which has room, and respects the taint: node-3 isn’t even considered. Within seconds the API is back to 3 ready replicas.

kubectl get pods -o wide

Step 7 · ConceptThe old pod stays Terminating

The old API pod keeps showing as Terminating, and can stay like that for hours. To disappear for good, node-3’s kubelet would have to confirm it stopped the container, and it isn’t there to answer.

For a Deployment this doesn’t matter: it already created the replacement and doesn’t count pods being deleted. The “zombie” pod just takes up a line in kubectl.

Watch out: Pods stuck in Terminating on a NotReady node are normal. It doesn’t mean the cluster is stuck.

Step 8 · ProblemThe database doesn’t come back on its own

db-0 is different. A StatefulSet promises there will never be two pods with the same name at the same time. While the old db-0 is Terminating, it won’t create another db-0.

And the cluster can’t tell whether the machine died or just lost its network, with the database still writing to disk. A second db-0 could mean two databases writing to the same data.

Key idea: For a Deployment, a dead node fixes itself in about 6 minutes. For a StatefulSet, someone has to confirm the machine is really dead.

kubectl get pods -l app=db

Step 9 · ProblemForcing the delete isn’t enough

Many people force the delete: kubectl delete pod db-0 --force --grace-period=0. The old pod disappears from the cluster and the StatefulSet creates the new db-0 on node-2.

But the database disk (ReadWriteOnce) is still recorded as attached to node-3. The new pod sits in ContainerCreating with a Multi-Attach error, because an RWO volume can only be attached to one node at a time. Kubernetes waits another 6 minutes before force-detaching it.

Watch out: --force only deletes the record in the cluster; it doesn’t shut anything down. Use it only when you’re sure the machine is off, or you may end up with two databases on the same disk.

kubectl delete pod db-0 --force --grace-period=0

Step 10 · SolutionThe right way: say the node is dead

Since version 1.28 there’s an official way: after confirming the machine is off, you put the node.kubernetes.io/out-of-service taint on the node.

It’s like telling the cluster “trust me, this machine isn’t coming back soon”. Kubernetes immediately deletes the stuck pods, detaches the volumes and lets the StatefulSet recreate db-0 on another node, without waiting the 6 minutes.

Good to know: In the cloud, when the VM is deleted, the cloud controller manager usually removes the Node object from the cluster, with a similar effect.

kubectl taint nodes node-3 node.kubernetes.io/out-of-service=nodeshutdown:NoExecute

Step 11 · SolutionThe machine comes back, but stays empty

The power supply was replaced and node-3 booted again. The kubelet reports in again, the node turns Ready and the unreachable taints go away on their own. The out-of-service taint you remove by hand.

Pods don’t move back to node-3: Kubernetes doesn’t rebalance what’s already running. node-3 only gets new pods from now on. To spread things out again, use kubectl rollout restart or a tool like the descheduler.

kubectl taint nodes node-3 node.kubernetes.io/out-of-service-

Step 12 · SummarySummary: the timeline of a dead node

When a node goes down, Kubernetes first gets suspicious, then isolates it, and only then recreates. Every stage has a timer, and all of them can be tuned.

To suffer less: run at least 2 replicas, spread them across nodes (topologySpreadConstraints or anti-affinity) and use retries. A PodDisruptionBudget doesn’t protect against a machine dying; it only applies to planned evictions such as a drain.
