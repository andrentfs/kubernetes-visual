Pods and Deployments

The smallest piece of Kubernetes, why it’s disposable, and how the cluster keeps copies alive.

11 minBeginner12 steps

▶ Open the interactive lesson

This is the text version. The interactive lesson has the animated diagram for each step.

You will learn

  • Know what a pod is
  • Know when to put containers in the same pod
  • Understand why pods are disposable
  • Use a Deployment to keep copies alive
  • Watch the cluster recover from a lost machine

Step by step

Step 1 · ConceptThe pod: Kubernetes’ smallest piece

Kubernetes doesn’t run bare containers. It wraps the container in a pod, which gets its own IP address and is the unit the cluster starts, moves and stops.

A pod is like a pea pod: a little shell with one or more peas inside. Most of the time a pod holds a single container.

Key idea: The container is the packaged program. The pod is the apartment it lives in inside the cluster, with its own address and resources.

kubectl run api --image=loja/api:1.0

Step 2 · ConceptTwo containers, one pod

Sometimes two containers need to live side by side. Example: the API writes logs to a file, and a second container reads that file and ships the logs to a monitoring system.

Containers in the same pod share an address (they talk over localhost) and can share a folder, called a volume. The helper is called a sidecar, like the little car attached to a motorbike.

Step 3 · ConceptWhen to group and when to split

Rule of thumb: only put two containers in the same pod if they need to be born, grow and die together.

The website and the database aren’t like that. The website needs 3 copies at peak time; the database needs just one. If they shared a pod, every website copy would drag a database along. So they live in separate pods.

Good to know: When in doubt, split. Separate pods grow, update and fail independently.

Step 4 · ProblemPods are disposable

The node rebooted for a system update and the API pod died with it. It doesn’t come back on its own: a hand-made pod has nobody looking after it.

Kubernetes doesn’t try to repair a dead pod. It prefers to throw it away and create a new one.

Watch out: Never keep important data only inside a pod. When the pod goes, everything inside goes with it.

kubectl get pods

Step 5 · ConceptCattle, not pets

If your cat gets sick, you take it to the vet: it’s one of a kind. In a herd of a thousand, every animal is treated as replaceable. Kubernetes treats pods like a herd.

A replacement pod is born with a different name and a different IP address (from 10.1.0.12 to 10.1.0.47). So nothing should depend on the address of one particular pod.

Key idea: Pods come and go. What stays stable is the description of what you want, not the pod itself.

Step 6 · SolutionDeployment: the written order

Instead of creating pods by hand, you write a Deployment: a YAML file (a simple text format) that says “I want 3 copies of the loja/api:1.0 image”.

You send the file with kubectl apply. The API server checks it and writes the order into etcd. No pod exists yet, but the wish is on record.

Key idea: The Deployment is the recipe with a quantity. It isn’t a pod: it makes sure the pods exist.

kubectl apply -f deployment.yaml

Step 7 · ConceptThe copies spread out

The Deployment creates a ReplicaSet, a counter whose only job is to keep the right number of copies. The ReplicaSet creates 3 pods, and the scheduler puts each one on a different node.

Spreading out is on purpose: if one machine goes down, the other copies keep serving.

Good to know: Copies of a pod are called replicas. For anything important, use at least 2; 3 is the most common.

Step 8 · ProblemA pod fails

A bug made the API use too much memory. The node kills the container to protect its neighbours; on the dashboard this shows up as OOMKilled, “killed for running out of memory”.

The ReplicaSet controller notices right away: desired is 3, actual is now 2.

kubectl get deploy api

Step 9 · SolutionA replacement appears on its own

The ReplicaSet creates a new pod, the scheduler picks a node and, within seconds, the count is back to 3.

Nobody was woken up, no script ran. This is called self-healing.

Key idea: You never say “restart that pod”. You say “I want 3”, and the system chases that number.

Step 10 · ProblemWhat if a whole machine dies?

node-3 had a hardware fault and stopped answering. Its kubelet sends no more news, and the control plane marks the node NotReady.

Kubernetes waits a little, about 5 minutes by default, because it might just be a brief network blip. After that, it gives up on that node’s pods.

Watch out: During that wait the app runs one copy short. That’s why extra replicas matter.

Step 11 · SolutionThe pods move house

The ReplicaSet creates a replacement and the scheduler puts it on a healthy node, node-1. Actual matches desired again.

When node-3 comes back, it simply gets new pods in the future. Nothing has to be “moved back”.

kubectl get pods -o wide

Step 12 · SummarySummary: Pod, ReplicaSet and Deployment

Day to day you only write Deployments. ReplicaSets and pods are created from them.

Good to know: Databases and other apps that store data use a cousin of the Deployment, the StatefulSet, which gives each copy a fixed name and disk.
