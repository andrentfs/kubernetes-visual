Security and RBAC

Who can do what in the cluster: users, ServiceAccounts, Roles, ClusterRoles and their bindings.

Step by step

Step 1 · ContextAt first, everyone is admin

The store now has two areas in the cluster, separated by namespaces: “loja” (the website) and “financeiro” (payments). A namespace is like a folder: it groups one team’s resources.

To keep things simple, developer Ana and the deploy robot (ci-bot) were given cluster-admin: they can read, change and delete anything in any namespace.

Good to know: Namespaces alone protect nothing. They organise; RBAC is what protects.

kubectl get clusterrolebindings

Step 2 · ProblemOne command in the wrong place

Ana wanted to clean up test pods in her namespace, but her terminal was pointing at “financeiro”. One kubectl delete pods --all and payments went down.

Nobody acted in bad faith. The problem was access: she could do something her job never required.

Watch out: Too much permission turns any typo, or leaked password, into a serious incident.

kubectl delete pods --all -n financeiro

Step 3 · ConceptEvery request goes through 3 gates

Every request to the API server goes through three stages, in order. Authentication: who are you? (certificate, token, or company login via OIDC). Authorization: are you allowed to do this? (this is where RBAC comes in).

Admission: does the request follow the cluster’s rules? Admission controllers can reject it (for example, a pod without resource limits) or adjust it before it’s saved.

Key idea: Fail the first gate: 401 Unauthorized. Pass the first and get stopped at the second: 403 Forbidden.

Step 4 · ConceptWho asks: users, groups and ServiceAccounts

Kubernetes has no list of people. A user (like “ana”) and their groups (like “devs”) come from outside: from the certificate or the login provider.

Programs running inside the cluster use ServiceAccounts instead: identities created by Kubernetes itself, one or more per namespace, for robots and pods.

Good to know: These three are called subjects. Every RBAC permission is given to a subject.

Step 5 · ConceptRole: the list of what’s allowed

A Role is a list of rules inside one namespace. Each rule says which resources (pods, services, secrets…) and which verbs (get, list, watch, create, update, patch, delete).

Here, the Role “leitor-pods” in the loja namespace allows only get, list and watch on pods. It doesn’t apply to anyone yet: it’s just the list.

Key idea: RBAC only adds permissions. There is no “deny” rule: anything not in some Role is forbidden.

kubectl create role leitor-pods --verb=get,list,watch --resource=pods -n loja

Step 6 · ConceptRoleBinding: handing the list to someone

A RoleBinding connects a Role to one or more subjects. It’s like handing the right badge to the right person.

The RoleBinding “ana-leitora” says: user ana gets the Role leitor-pods in the loja namespace. Now the rule applies.

kubectl create rolebinding ana-leitora --role=leitor-pods --user=ana -n loja

Step 7 · SolutionAllowed here, not there

Ana lists the store’s pods: it works. She tries to delete a pod in financeiro: the API server answers 403 Forbidden, and nothing happens.

To check without risk, use kubectl auth can-i. With --as, an admin can test someone else’s permissions.

Good to know: The principle of least privilege: everyone gets only what their own job needs, and nothing more.

kubectl auth can-i delete pods -n financeiro --as ana

Step 8 · ConceptClusterRole: rules for the whole cluster

Some things don’t live in any namespace, like nodes and PersistentVolumes. Other times, someone needs to read every namespace. That’s what a ClusterRole is for.

Prometheus (monitoring) needs to read everything. A ClusterRoleBinding connects the “view” ClusterRole to its ServiceAccount, across the whole cluster.

Watch out: A ClusterRoleBinding to cluster-admin is the cluster’s master key. Review who has one, regularly.

kubectl create clusterrolebinding monitor-view --clusterrole=view --serviceaccount=monitoring:prometheus

Step 9 · ConceptOne ClusterRole, many namespaces

A handy trick: a RoleBinding can point to a ClusterRole. Then the ClusterRole’s rules apply only inside that RoleBinding’s namespace.

That way you write the list once (the “view” ClusterRole) and hand it out per namespace, with one RoleBinding in each.

Step 10 · ConceptPods have identities too

Every pod runs as a ServiceAccount. If you don’t pick one, it uses the namespace’s “default”, which has no RBAC permissions.

When an app needs to talk to the API server (an operator, a deploy tool), create its own ServiceAccount, give it a small Role and set it on the pod with serviceAccountName.

Good to know: If the pod doesn’t talk to the API server, set automountServiceAccountToken: false. Fewer credentials inside the container means less risk if it’s compromised.

Step 11 · Trade-offTrade-off: careful with Secrets

Secrets hold passwords and keys. But by default their content is only base64, which is an encoding, not encryption: whoever reads the Secret reads the password.

So get or list permission on secrets is the same as having the passwords. And anyone who can create pods in a namespace can mount any Secret from it inside a pod.

Watch out: Turn on etcd encryption at rest, don’t grant list/get on secrets without need, and remember the “view” ClusterRole deliberately leaves Secrets out.

kubectl auth can-i get secrets -n financeiro --as ana

Step 12 · SummarySummary: the pieces of RBAC

Build permissions from the ground up: the minimum needed, per namespace, reviewed regularly.

Good to know: In the exam: kubectl create role, create rolebinding and auth can-i --as solve most RBAC tasks without hand-writing YAML.
