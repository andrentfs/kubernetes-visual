Updating without downtime

Ship a new version while the store is busy, without a second offline, and roll back if it goes wrong.

11 minIntermediate11 steps

▶ Open the interactive lesson

This is the text version. The interactive lesson has the animated diagram for each step.

You will learn

  • Understand why stopping everything to update is bad
  • Know how a rolling update works
  • Undo a bad version with a rollback
  • Tell readiness and liveness probes apart

Step by step

Step 1 · ContextVersion 2.0 is ready

The store runs 3 pods of version 1.0 of the API. The team has finished 2.0, with a new cart, and wants to ship it this afternoon while the store is busy.

Shipping a new version is the riskiest moment in a system’s life. Let’s see why, and how Kubernetes makes it calm.

Step 2 · ProblemThe old way: close the shop

The simplest way is to switch off all the 1.0 pods and then start the 2.0 ones. In between, there’s nobody to serve customers.

For a few minutes, every customer sees an error page. That’s why updates used to happen in the middle of the night, with an “under maintenance” notice.

Watch out: Stopping everything to update means going offline with every new version. With several releases a week, that becomes a serious problem.

Step 3 · SolutionRolling update: one at a time

A Deployment does better by default. When you change the image, it creates a 2.0 pod before switching off any 1.0 pod.

The three old pods keep serving while the new one starts. This gradual swap is called a rolling update.

kubectl set image deployment/api api=loja/api:2.0

Step 4 · ConceptReadiness probe: “can I serve yet?”

Started isn’t the same as ready. Version 2.0 needs a few seconds to load settings and connect to the database.

The kubelet keeps asking the new pod, at an address like /health, whether it’s ready. Only when the answer is yes does the pod join the Service and start getting customers.

Watch out: Without a readiness probe, Kubernetes would send customers to a pod that’s still loading, and they’d see errors.

Step 5 · SolutionReady? Then an old one leaves

The 2.0 pod answered 200 OK, the success code, and joined the Service. Only now is one 1.0 pod switched off.

At no point did the store have fewer than 3 ready pods.

Step 6 · Trade-offTrade-off: two versions at once

The cycle repeats: start a 2.0, wait until it’s ready, switch off a 1.0. For a few minutes, customers are served sometimes by the new version, sometimes by the old one.

If 2.0 changed the format of some data, 1.0 must still understand it, and vice versa.

Watch out: Database and API changes must be compatible with the previous version, because both run together for a while.

Step 7 · SolutionVersion 2.0 is live

All three pods are on 2.0 and no customer noticed the swap: zero seconds offline.

Two settings control the pace: maxSurge (how many extra pods may exist during the swap) and maxUnavailable (how many may be missing).

kubectl rollout status deployment/api

Step 8 · ProblemOops: 2.0 has a bug

Half an hour later, support calls: some customers can’t pay. 2.0 has a bug that only shows up with certain cards, and some requests come back with error 500, “server error”.

The readiness probe didn’t catch it, because /health answered normally. Probes check that the pod is alive, not that the code is right.

Watch out: Automated tests and error monitoring are still essential. Kubernetes guarantees a smooth swap, not code quality.

Step 9 · SolutionRollback: back in one command

The Deployment keeps previous versions. A single command takes you back: rollout undo.

It’s the same rolling update in reverse: start 1.0 pods, wait until they’re ready, switch off the 2.0 ones. In a minute or two the store is back as it was, without going offline.

Key idea: Because going back is easy and safe, shipping new versions stops being scary. Teams that release often depend on this.

kubectl rollout undo deployment/api

Step 10 · ConceptLiveness probe: “are you still alive?”

Sometimes a program freezes without dying: the process is still running, but it doesn’t answer anything. To the operating system, it looks alive.

The liveness probe is another kubelet health check: “do you still answer?”. If the pod fails a few times in a row, the kubelet restarts the container. Readiness takes it out of the Service; liveness restarts it.

Step 11 · SummarySummary: updating without fear

The frozen container was restarted by the kubelet and rejoined the Service on its own.

Good to know: For even more careful releases there are strategies like canary (sending only 5% of customers to the new version) and blue-green (two full copies, instant switch).
