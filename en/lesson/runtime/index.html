Runtime security: Falco, threats and auditing

Even with everything protected, something can slip through. Detecting odd behaviour, investigating the attack, making containers immutable and recording who did what.

Step by step

Step 1 · ContextSomeone opened a shell in the pod

An attacker managed a kubectl exec into the api pod and opened a shell. From there they can read the ServiceAccount token, download tools and look for other targets.

No firewall sees this: it’s just a new process inside a container that was already running.

kubectl exec -it api -- sh

Step 2 · ConceptFalco: watching calls to the kernel

Falco runs on every node (usually as a DaemonSet) and watches the syscalls of all containers with eBPF.

Rules are YAML: condition describes the event, output the message and priority the severity. Your own rules go in /etc/falco/falco_rules.local.yaml (or the rules.d folder), without touching the defaults.

Step 3 · SolutionThe alert and the response

The default rule “Terminal shell in container” fires and shows the container, the command and the pod details. Read the alert in Falco’s logs: journalctl -u falco, or kubectl logs on the Falco pod.

With the container ID, crictl ps --id <id> and crictl inspect lead to the pod. Exam tasks often ask you to isolate or delete the pod and write the answer to a file.

Watch out: Changing a rule’s output (for example, adding %k8s.pod.name) is a common task. Restart Falco after editing.

journalctl -u falco --since "10 min ago"

Step 4 · ConceptThreats in each layer

The curriculum asks you to detect threats across infrastructure, applications, networks, data, users and workloads. Each one leaves a different trail.

Step 5 · ConceptInvestigating the phases of an attack

Attacks follow phases: initial access, execution, persistence, privilege escalation, lateral movement and data theft. MITRE ATT&CK and Microsoft’s threat matrix for Kubernetes organise these phases.

To reconstruct what happened, cross-check the Falco alert, the container logs and the API server audit log.

Key idea: Keep the evidence before deleting the pod: logs, describe and the alert. Once the pod is gone, the container is gone.

Step 6 · SolutionImmutable container

An immutable container can’t be changed after it starts: readOnlyRootFilesystem: true, and emptyDir only where the app needs to write (such as /tmp).

Combine it with runAsNonRoot, allowPrivilegeEscalation: false and an image with no shell. The attacker may get in, but can’t write tools or change the app.

kubectl get pod api -o jsonpath='{.spec.containers[*].securityContext}'

Step 7 · ConceptAudit log: who did what

The API server can record every request: who asked, for what, when and with what result. An audit Policy sets the level for each case: None, Metadata, Request or RequestResponse.

Rules are read in order and the first match wins. For Secrets, use Metadata: logging the body would write the password to the log.

Step 8 · SolutionTurning auditing on

On the kube-apiserver: --audit-policy-file=/etc/kubernetes/audit/policy.yaml and --audit-log-path=/var/log/kubernetes/audit/audit.log, plus --audit-log-maxage, --audit-log-maxbackup and --audit-log-maxsize for rotation.

The static pod must see those paths: add hostPath volumes and volumeMounts for the policy and the log folder.

Watch out: Forgot the volume? The API server won’t start. Check with crictl ps -a and the logs in /var/log/pods.

grep audit /etc/kubernetes/manifests/kube-apiserver.yaml

Step 9 · ProblemFinding who did it

A Secret was deleted. Each line of audit.log is JSON: look for verb delete with resource secrets, and read user.username, sourceIPs and requestReceivedTimestamp.

Here it was the ci-bot ServiceAccount, which had more permissions than it needed. The fix goes into RBAC.

grep '"resource":"secrets"' /var/log/kubernetes/audit/audit.log | grep '"verb":"delete"'

Prevention is never complete. Make sure you can see what happens inside containers and who touched the API.
