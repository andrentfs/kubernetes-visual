Scheduling: resources, affinity and taints

How to decide where each pod runs: CPU and memory bookings, quotas, labels, affinities, taints and node maintenance.

Step by step

Step 1 · ContextRecap: who picks the node

Every new pod without a node goes through the scheduler. It rules out nodes that won’t do and scores the rest.

In this lesson you’ll learn to influence that choice: say how much the pod needs, where it may run and where it may not.

Step 2 · ConceptRequests, limits and QoS

A request is the booking: the scheduler only places the pod on a node with that much free. A limit is the ceiling: going over the CPU limit slows the container down (throttling); going over the memory limit kills it (OOMKilled).

From the combination, the pod gets a QoS class: Guaranteed (request equals limit), Burstable (some values set) or BestEffort (nothing set).

Key idea: When a node runs short of memory, the kubelet evicts BestEffort pods first, then Burstable. Guaranteed go last.

Step 3 · ProblemPods without limits hurt their neighbours

A reporting job was created with no requests or limits. The scheduler thought it needed nothing and put it on node-2, which was already full.

The job ate all the memory. The kubelet started evicting pods to save the node.

Watch out: Without requests, the scheduler works blind. Without limits, one pod can eat the whole node.

Step 4 · SolutionLimitRange and ResourceQuota

A LimitRange sets default and maximum values per container in a namespace. Pods without requests get the defaults automatically.

A ResourceQuota sets the namespace’s total: for example, at most 4 booked CPUs and 10 pods. Requests above that are refused with “exceeded quota”.

Good to know: With a CPU or memory quota in place, every pod in the namespace must declare requests, or it’s refused. A LimitRange with defaults avoids that.

kubectl create quota loja --hard=requests.cpu=4,pods=10 -n loja

Step 5 · ConceptnodeSelector: choosing by label

Nodes have labels too. You tag node-2 with disktype=ssd and, in the pod, write nodeSelector: disktype: ssd.

The scheduler only considers nodes with that label. If none have it, the pod stays Pending.

kubectl label node node-2 disktype=ssd

Step 6 · ConceptNode affinity: richer rules

Node affinity does what nodeSelector does, with more options: operators like In, NotIn and Exists, and two levels.

requiredDuringSchedulingIgnoredDuringExecution is mandatory. preferredDuringSchedulingIgnoredDuringExecution is a weighted preference: the scheduler tries, but uses another node if it has to.

Good to know: “IgnoredDuringExecution” means that if the node’s label changes later, the pod already running isn’t removed.

Step 7 · ConceptAffinity between pods

You can also decide relative to other pods. podAntiAffinity with topologyKey: kubernetes.io/hostname says: “don’t put two replicas on the same node”.

podAffinity does the opposite: it brings together pods that talk a lot, like the app and its cache.

Key idea: Anti-affinity spreads replicas: if a node goes down, only one copy goes with it.

Step 8 · ConceptTaints and tolerations: the “keep out” sign

A taint is a mark on a node that repels pods. kubectl taint nodes node-3 gpu=true:NoSchedule makes the scheduler avoid node-3.

Only pods with a matching toleration get in. That’s how expensive nodes, like GPU ones, stay reserved.

EffectWhat it does
NoScheduleDoesn’t schedule new pods
PreferNoScheduleAvoids it if possible
NoExecuteAlso evicts pods already there
kubectl taint nodes node-3 gpu=true:NoSchedule

Step 9 · Trade-offTrade-off: tolerating isn’t being attracted

The machine-learning pod has the toleration, but the scheduler put it on node-2. A toleration only allows entry to the tainted node; it doesn’t force it.

To make sure it lands on the GPU node, combine the toleration with node affinity (or nodeSelector) pointing at that node.

Watch out: Taints keep others out. Affinity pulls the right one in. To reserve a node, use both.

Step 10 · ConceptMaintenance: cordon and drain

kubectl cordon node-2 marks the node SchedulingDisabled: nothing new gets in, and what’s there keeps running.

kubectl drain node-2 cordons it and also moves the pods out safely, so they’re recreated on other nodes. After maintenance, kubectl uncordon opens it up again.

Watch out: Drain stops on DaemonSet pods and pods with emptyDir. Use --ignore-daemonsets and --delete-emptydir-data, knowing what each one does.

kubectl drain node-2 --ignore-daemonsets --delete-emptydir-data

Step 11 · ConceptStatic pods and nodeName

The control plane components (etcd, API server, scheduler) are static pods: YAML files in /etc/kubernetes/manifests that the kubelet starts on its own, without the scheduler.

And nodeName on a pod skips the scheduler: the pod goes straight to the given node. Useful when the scheduler is down.

Key idea: A static pod shows up in kubectl with the node name at the end (like etcd-controlplane). To change it, edit the file; deleting it with kubectl doesn’t help.

Step 12 · SummarySummary: how to influence the scheduler

Resources say how much, labels and affinities say where, taints say where not.

FeatureEffect
requests/limitsBooking and ceiling per container
LimitRange/QuotaDefaults and totals per namespace
nodeSelector/affinityPulls to certain nodes
taint/tolerationKeeps away from certain nodes
cordon/drainTakes a node out of use
