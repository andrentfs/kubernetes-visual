Service and Ingress

Pods change address all the time. How does the website find the API, and how does the internet find the store?

11 minBeginner11 steps

▶ Open the interactive lesson

This is the text version. The interactive lesson has the animated diagram for each step.

You will learn

  • Understand why you don’t use a pod’s address
  • Use a Service as a fixed name
  • See the Service steer around sick pods
  • Open the app to the internet with an Ingress

Step by step

Step 1 · ContextThe website talks to the API

When someone opens the store, the website pod (web) asks the API for the product list and prices. Right now there are 3 API pods spread across the nodes.

For now, the website has been configured with the IP address of each API pod, written down by hand.

Step 2 · ProblemThe addresses change

An API pod was recreated and got a new address: it was 10.1.2.7, now it’s 10.1.2.9. The website keeps calling the old number, and requests get lost.

Remember the last lesson? Pods are disposable. Anything that depends on a pod’s IP breaks at the first swap.

Watch out: Writing down pod IPs is like writing down a temp worker’s desk extension: next week someone else answers, or nobody does.

Step 3 · SolutionService: a name that doesn’t change

A Service gives the pods a fixed name, like “api”, and an address that never changes. The website now calls http://api and doesn’t need to know which pods are behind it.

It’s like a call-centre number: you always dial the same number, and the centre puts you through to whoever is free.

Key idea: The Service is stable; the pods behind it change all the time. Whoever calls the Service doesn’t even notice.

kubectl expose deployment api --port=80

Step 4 · ConceptTags: how the Service finds pods

Every pod carries tags called labels, like app=api or app=web. The Service has a filter, the selector, that says: “I want every pod with app=api”.

A new pod with the right tag joins the list on its own. A pod that dies leaves on its own. That list lives in EndpointSlice objects (the old Endpoints object has been deprecated since v1.33).

Good to know: Labels are the glue of Kubernetes: Services, Deployments and many tools find things by tag, not by name.

Step 5 · ConceptThe Service shares out the work

Each request to http://api goes to one of the pods on the list. On average each pod gets a third of the work, and they all sit at a similar CPU, around 34%.

This is called load balancing: spreading requests so nobody is overloaded while someone else sits idle.

Step 6 · ProblemA pod gets sick

One of the pods lost its connection to the database. It’s running, but it answers with errors. The kubelet runs a health check called a readiness probe (“are you ready to serve?”) and gets a no.

Meanwhile, some requests still land on that pod and fail.

Watch out: A running pod is not the same as a healthy pod. Without a readiness probe, Kubernetes can’t tell the difference.

Step 7 · SolutionSick pods leave the list at once

As soon as the readiness probe fails, the pod is removed from the Service’s endpoints. Nobody sends it requests any more.

The other two pods take over the work (CPU goes up to 50%). When the sick pod recovers and passes the probe, it rejoins the list on its own.

kubectl get endpointslices -l kubernetes.io/service-name=api

Step 8 · ProblemWhat about people outside the cluster?

The Service we created is a ClusterIP: its address only works inside the cluster. For your customers, out on the internet, the store simply doesn’t exist.

We need a public front door.

Step 9 · SolutionIngress: the building’s front desk

An Ingress is the cluster’s front desk. It receives internet traffic on a public address and forwards it to the right Service.

Behind it runs a program called an Ingress Controller, such as NGINX or Traefik, which does the actual work.

Good to know: Kubernetes is replacing Ingress with the Gateway API, which is more modern and flexible. The idea is the same: a front door with rules.

kubectl get ingress

Step 10 · ConceptOne address, many destinations

The front desk reads each visitor’s address and decides where to send them: loja.com/ goes to the web Service (the pages); loja.com/api goes to the api Service (the data).

It also handles the padlock in the browser: the HTTPS certificate that keeps the connection encrypted.

Key idea: A single public address serves the whole site. To add a new area, you just add a new rule to the Ingress.

Step 11 · SummarySummary: ways to expose an app

In practice: ClusterIP for internal conversations and Ingress for whatever comes from the internet.
