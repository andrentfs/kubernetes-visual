System hardening: host, ports, AppArmor and seccomp

A node is just another Linux machine. Fewer packages, fewer ports and fewer privileges, plus kernel profiles that limit what a container can do.

13 minAdvanced10 steps

You will learn

  • Cut the node’s packages, services and ports
  • Know which ports Kubernetes uses
  • Close the rest with a firewall
  • Apply least-privilege identity
  • Use AppArmor and seccomp in pods

Step by step

Step 1 · ContextWhat runs on the node

Besides the kubelet and containerd, node-1 runs sshd, an apache2 left over from a test and cups (printing). Every service is an open port and one more program that can have bugs.

ss -tlnp lists the listening TCP ports and the process behind each one.

ss -tlnp

Step 2 · SolutionRemoving what isn’t needed

systemctl disable --now stops the service and removes it from boot. If the package isn’t used, remove it with apt remove (or your distribution’s package manager).

Do the same with users, compilers and tools that would only help an attacker.

systemctl disable --now apache2 cups

Step 3 · ConceptThe ports Kubernetes uses

On the control plane: 6443 (API server), 2379-2380 (etcd), 10250 (kubelet), 10259 (scheduler) and 10257 (controller-manager). On workers: 10250 (kubelet) and the NodePort range, 30000-32767.

Your CNI may need other ports; check its documentation.

Step 4 · SolutionClosing the rest with a firewall

With ufw: ufw default deny incoming, then ufw allow 6443/tcp (and the other ports the node needs). In the cloud, do the same in the security group.

etcd should only be reachable by the API server, never from outside.

Watch out: Before ufw enable, allow port 22 if you are connected over SSH, or you lose access.

ufw default deny incoming

Step 5 · ConceptLeast-privilege identity and access

On the node: only the users you need, SSH with keys only, and sudo just for administrators. id ana shows a user’s groups.

In the cloud: the machine’s IAM role should have only the permissions the kubelet and agents use. Inside the cluster, the same applies to RBAC.

Key idea: An attacker who reaches the node inherits everything the node can do, including in the cloud account.

id ana

Step 6 · ConceptAppArmor: limiting what a process can access

AppArmor is a kernel security module. A profile says which files, capabilities and network access a program may use.

The profile is loaded on the node (apparmor_parser -q file), and aa-status lists the loaded ones. Kubernetes doesn’t load profiles: that’s done on each node.

aa-status

Step 7 · SolutionApplying the profile to the pod

In the pod or container securityContext: appArmorProfile with type: Localhost and localhostProfile: k8s-deny-write. There are also the RuntimeDefault and Unconfined types.

With a profile that denies writes, kubectl exec web -- touch /tmp/x fails with Permission denied: the kernel blocked it.

kubectl exec web -- touch /tmp/x

Step 8 · Trade-offTrade-off: the profile must be on every node

Pod web-2 landed on worker-2, where the profile wasn’t loaded. The kubelet refuses to start the pod, and kubectl describe shows the AppArmor error.

Load the profile on every node that may get the pod, or pin the pod to the right nodes with nodeSelector or affinity.

Watch out: A profile loaded by hand disappears on reboot if its file isn’t in /etc/apparmor.d.

kubectl describe pod web-2

Step 9 · Conceptseccomp: filtering calls to the kernel

seccomp limits which system calls (syscalls) a container can make. seccompProfile with type: RuntimeDefault uses the container runtime’s default profile, which blocks dangerous and rare calls.

For a custom profile, use type: Localhost with localhostProfile set to a file path under /var/lib/kubelet/seccomp on the node.

Good to know: The restricted Pod Security Standard requires RuntimeDefault. It’s the safe choice for almost every app.

Step 10 · SummarySummary: a node with less surface

Remove what isn’t used from the node, close the remaining ports and limit each container with AppArmor and seccomp.
