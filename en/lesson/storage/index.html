Storage: volumes, PV, PVC and StorageClass

Containers forget everything when they restart. How to keep data that survives pods, restarts and machine changes.

13 minIntermediate12 steps

This is the text version. The interactive lesson has the animated diagram for each step.

You will learn

  • Understand why the container’s disk is temporary
  • Meet emptyDir and hostPath
  • Tell a PersistentVolume from a PersistentVolumeClaim
  • Know the access modes
  • Use a StorageClass to create disks automatically
  • Mind the reclaim policy

Step by step

Step 1 · ProblemThe database lost everything

The database pod kept its data inside its own container. The pod died, a new one was born, and the database started empty.

A container’s file system only lasts as long as the container. It’s like writing on a whiteboard that gets wiped at every restart.

Watch out: Never keep important data on the container’s disk. It’s disposable, just like the pod.

Step 2 · ConceptemptyDir and hostPath: the simple volumes

An emptyDir volume is born empty with the pod and lasts as long as the pod. It’s for caches, or for two containers in the same pod to share files. It survives container restarts, but not the pod dying.

A hostPath volume uses a folder on the node itself, like /data. The data stays on the machine even if the pod dies.

Good to know: emptyDir can even live in memory (medium: Memory), useful for fast temporary files.

Step 3 · ProblemThe trouble with hostPath

The database pod was rescheduled onto node-2. The data is still in node-1’s /data folder, and the new pod starts empty again.

On top of that, accessing node folders is a security risk. hostPath is for system cases (log agents, for example), not for application data.

Watch out: Application data needs a disk that follows the pod wherever it goes.

Step 4 · ConceptPersistentVolume: a disk for the cluster

A PersistentVolume (PV) represents a real piece of storage: a cloud disk, an NFS folder, a storage volume. It exists on its own, outside any pod.

A PV belongs to no namespace. It has a size (like 10Gi), access modes and a reclaim policy.

Key idea: The PV is the cluster admin’s side: “this disk exists and is available”.

kubectl get pv

Step 5 · ConceptPersistentVolumeClaim: the app’s request

The app doesn’t pick a specific disk. It makes a request, the PersistentVolumeClaim (PVC): “I want 5Gi, for one node at a time”.

Kubernetes looks for a free PV that meets the request and binds the two. From then on, both have status Bound: that PV belongs only to that PVC.

Good to know: The PVC lives in a namespace, alongside the app. The PV lives in the cluster. Splitting them lets the app team ask for disk without knowing infrastructure details.

kubectl get pvc

Step 6 · SolutionThe pod uses the PVC

In the pod, the volume points to the PVC: persistentVolumeClaim.claimName: dados, mounted at /var/lib/postgresql/data.

If the pod dies and another is born, even on another node, it mounts the same PVC and finds the data there.

Key idea: Pod → PVC → PV → real disk. The pod only knows about the PVC.

Step 7 · ConceptAccess modes

An ordinary cloud disk can only be mounted by one node at a time: ReadWriteOnce (RWO). If a second pod on another node tries to use it, it waits.

For many nodes at once you need network storage that supports it, like NFS, with ReadWriteMany (RWX).

ModeShortWho mounts
ReadWriteOnceRWO1 node, read and write
ReadOnlyManyROXMany nodes, read only
ReadWriteManyRWXMany nodes, read and write
ReadWriteOncePodRWOP1 pod only

Step 8 · ConceptStorageClass: disks on demand

Creating PVs by hand doesn’t scale. A StorageClass describes a kind of disk (for example, cloud SSD) and which provisioner, usually a CSI driver, knows how to create it.

When a PVC asks for storageClassName: rapido, the provisioner creates the disk and the PV automatically. That’s dynamic provisioning.

Good to know: One StorageClass can be the cluster default. PVCs without a storageClassName use the default.

kubectl get storageclass

Step 9 · ConceptWaitForFirstConsumer: creating the disk in the right place

Cloud disks live in one zone. If the disk is born in zone A and the pod goes to zone B, the pod can’t mount it.

With volumeBindingMode: WaitForFirstConsumer, the PVC stays Pending until a pod uses it. Then the scheduler picks the node first and the disk is created in that node’s zone.

Watch out: A Pending PVC with this setting is normal until a pod exists. Don’t mistake it for an error.

Step 10 · Trade-offTrade-off: deleted the PVC, deleted the data?

The PV’s reclaim policy decides. With Delete, the default for dynamic provisioning, deleting the PVC deletes the PV and the real disk. The data is gone.

With Retain, the PV goes to status Released and the disk stays. An admin recovers the data or cleans up by hand before reusing it.

Watch out: For important data, use Retain on the StorageClass, or change the existing PV with kubectl patch before any clean-up.

kubectl patch pv pv-dados -p '{"spec":{"persistentVolumeReclaimPolicy":"Retain"}}'

Step 11 · ConceptGrowing a volume

The database grew. If the StorageClass has allowVolumeExpansion: true, just edit the PVC and change 10Gi to 20Gi.

The driver grows the disk. Shrinking isn’t possible: it can only grow.

kubectl edit pvc dados

Step 12 · SummarySummary: the data’s path

The pod asks the PVC, the PVC binds to a PV, and the PV points to the real disk, created by hand or by a StorageClass.
