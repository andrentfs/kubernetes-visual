Supply chain: images, SBOM and signatures

From code to pod, every stage can be attacked. Minimal images, vulnerability scans, SBOM, static analysis, signatures and allowed registries only.

Step by step

Step 1 · ContextFrom git to pod

Code goes to git, CI builds the image, the image goes to the registry and the cluster pulls it. An attacker can get in at any link: a malicious dependency, a compromised CI, an image swapped in the registry.

Supply Chain Security is worth 20% of the CKS.

Step 2 · ConceptMinimal base image

The less there is in the image, the fewer vulnerabilities and the fewer tools for an attacker. Use a multi-stage build: compile in a full image and copy only the result to a distroless or alpine base.

In the Dockerfile, set USER to an unprivileged user and pin the base version, never latest.

Good to know: Distroless images have no shell and no package manager. Whoever gets into the container has no tools.

podman build -t loja/api:v2 .

Step 3 · ProblemScanning for vulnerabilities

Trivy checks the image’s packages against databases of known vulnerabilities (CVEs). trivy image --severity HIGH,CRITICAL loja/api:v2 shows only the serious ones.

The output lists the package, the CVE, the installed version and the version that fixes it.

trivy image --severity HIGH,CRITICAL loja/api:v2

Step 4 · SolutionFixing and scanning again

Update the base image or the package to the fixed version, rebuild and scan again. Only then deploy.

In CI, Trivy can fail the build when it finds something serious: --exit-code 1 together with --severity CRITICAL.

trivy image --severity HIGH,CRITICAL loja/api:v3

Step 5 · ConceptSBOM: the list of ingredients

An SBOM (Software Bill of Materials) lists every component of an image: packages, libraries and versions. The most common formats are CycloneDX and SPDX.

trivy image --format cyclonedx --output sbom.json loja/api:v3 generates the SBOM. When a new CVE comes out, trivy sbom sbom.json tells you whether the image is affected without pulling it again.

trivy image --format cyclonedx --output sbom.json loja/api:v3

Step 6 · ConceptStatic analysis of manifests

Before apply, tools read the YAML and point out risks: privileged, running as root, no limits, hostPath.

kubesec scan pod.yaml returns a score and suggestions. kube-linter lint pod.yaml lists problems by rule. Both fit in CI.

kubesec scan pod.yaml

Step 7 · SolutionSigning and verifying images

With cosign, CI signs the image after the build: cosign sign --key cosign.key registry.loja.com/api@sha256:<digest>. The signature is stored in the registry itself.

Before deploying: cosign verify --key cosign.pub registry.loja.com/api:v3. A swapped or unsigned image fails verification.

cosign verify --key cosign.pub registry.loja.com/api:v3

Step 8 · SolutionOnly allowed registries

An admission controller rejects pods with images from elsewhere. With a ValidatingAdmissionPolicy (plus its binding), the CEL rule can be object.spec.containers.all(c, c.image.startsWith('registry.loja.com/')).

Another option, common in the exam, is ImagePolicyWebhook: the kube-apiserver asks an external service before accepting each image, configured through --admission-control-config-file.

Watch out: In ImagePolicyWebhook, defaultAllow: false rejects everything when the external service doesn’t answer. Check what the task asks for.

kubectl run x --image=docker.io/evil/miner

Step 9 · Trade-offTrade-off: tag or digest

A tag (api:v3) can be moved to another image in the registry. A digest (api@sha256:…) identifies exactly one content and never changes.

Pinning the digest guarantees you run what was scanned and signed, but every update means changing the digest in the manifest, ideally from CI.

kubectl set image deploy/api api=registry.loja.com/api@sha256:<digest>

Control each stage: what goes into the image, what it contains, who signed it and where it comes from.
