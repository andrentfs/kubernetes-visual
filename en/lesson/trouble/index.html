Cluster troubleshooting

The heaviest domain in the CKA: finding the problem methodically, from the pod to the node to the control plane.

14 minIntermediate11 steps

You will learn

  • Follow a fixed investigation routine
  • Fix ImagePullBackOff, Pending and CrashLoopBackOff
  • Find Services with no endpoints
  • Recover a NotReady node
  • Recover the control plane with crictl and the manifests

Step by step

Step 1 · ContextA routine for any problem

Under pressure, always follow the same order: kubectl get to see the state, describe to read the events, logs to see what the app said.

If the problem is the cluster itself, go one level down: the node (kubelet, runtime) and, last, the control plane components.

Key idea: The pod’s STATUS already tells you where to start: Pending is scheduling, ImagePullBackOff is the image, CrashLoopBackOff is the app or its config.

kubectl get pods -A | grep -v Running

Step 2 · ProblemImagePullBackOff: the image didn’t arrive

The node couldn’t pull the image. describe shows why in the events: wrong name or tag (nginx:1.2O, with the letter O), a private registry without a login, or the registry is down.

Fix the image in the Deployment (kubectl set image) or create the registry Secret and add it to imagePullSecrets.

Watch out: Read the Events section of describe. The exact message (not found, unauthorized) already shows the cause.

kubectl describe pod web

Step 3 · ProblemPending: nobody accepted the pod

A Pending pod hasn’t been scheduled. describe shows FailedScheduling and the reason: Insufficient cpu or memory, a tainted node without a toleration, a nodeSelector no node matches, or a PVC that didn’t bind.

The fix depends on the reason: lower requests, free up space, fix the label or toleration, or sort out the PVC.

Good to know: “0/3 nodes are available: 3 Insufficient cpu” means all 3 nodes were ruled out for the same reason.

Step 4 · ProblemCrashLoopBackOff: the app starts and dies

The container starts and exits right away, over and over. The current log may be empty; use kubectl logs --previous to see the run that crashed.

The exit code in describe helps: 137 is killed for lack of memory (OOMKilled) or by a kill; 1 is usually an app error; a wrong command or argument also shows up here.

Exit codeCommon cause
0Command finished (missing a loop?)
1Application error
127Command not found
137Killed: OOM or kill
kubectl logs api-7d9 --previous

Step 5 · ProblemA Service with no endpoints

The pods are Running, but nobody can reach the Service. kubectl get endpointslices -l kubernetes.io/service-name=web shows an empty ENDPOINTS column (<unset>).

It’s almost always the selector: the Service looks for app=wbe and the pods have app=web. Also check targetPort (the container’s port) and whether the pods pass readiness.

Watch out: Compare kubectl describe svc (Selector, TargetPort) with kubectl get pods --show-labels.

kubectl get endpointslices -l kubernetes.io/service-name=web

Step 6 · ProblemNode NotReady

node-3 shows NotReady in kubectl get nodes. With no news from the kubelet, the control plane stops sending pods there.

Log into the node (ssh) and check the kubelet: systemctl status kubelet. It may be stopped, unable to talk to the runtime, or misconfigured.

Watch out: In the exam the kubelet is often stopped or disabled on purpose. systemctl enable --now kubelet fixes both.

kubectl describe node node-3

Step 7 · SolutionReading the kubelet

journalctl -u kubelet shows why: a wrong certificate path, a broken config file, the wrong runtime socket.

The config lives in /var/lib/kubelet/config.yaml, and the credentials to talk to the API server in /etc/kubernetes/kubelet.conf. Fix it, restart, and watch the node go back to Ready.

systemctl restart kubelet

Step 8 · ProblemThe API server is down

kubectl answers “connection refused” on port 6443. Without the API server, kubectl doesn’t work, so you can’t use kubectl describe to investigate.

This usually comes from a mistake in the static pod manifest /etc/kubernetes/manifests/kube-apiserver.yaml: a wrong flag, a certificate path that doesn’t exist.

Watch out: The kubelet recreates the static pod on every change to the file. A typo there takes the API server down immediately.

Step 9 · Solutioncrictl: looking at containers without kubectl

With no API server, you go straight to the node’s runtime. crictl ps -a lists every container, including the ones that crashed; crictl logs <id> shows the error.

Logs are also in /var/log/pods and /var/log/containers. Fix the manifest and wait for the kubelet to restart the static pod.

Good to know: Before editing a manifest, save a copy outside the manifests folder. Extra .yaml files inside it also become pods.

crictl ps -a | grep kube-apiserver

Step 10 · ProblemScheduler or controller-manager down

If every new pod stays Pending with no scheduling event at all, the scheduler is down. If you scale a Deployment and nothing happens, suspect the controller-manager.

Both are static pods too. Check kubectl get pods -n kube-system and their logs, and fix the manifest.

Key idea: Pending with no FailedScheduling event = nobody tried to schedule it. That points to the scheduler, not the nodes.
