Anatomia de um cluster

Quem decide onde cada coisa roda? Uma visita guiada pela gerência e pela cozinha do cluster.

10 minIniciante11 passos

▶ Abrir a lição interativa

Esta é a versão em texto. A lição interativa tem o diagrama animado de cada passo.

Você vai aprender

  • Saber o que é um cluster e um node
  • Separar o control plane dos nodes
  • Conhecer API server, etcd, scheduler e controllers
  • Saber o que roda dentro de cada node

Passo a passo

Passo 1 · ConceitoUm cluster é um time de máquinas

Um cluster é um grupo de computadores que trabalham como se fossem um só. Cada computador do grupo é um node (nó, em português).

Seus containers rodam dentro de pods (a próxima lição explica em detalhe), e os pods ficam espalhados pelos nodes. Para você, tanto faz em qual máquina cada um está: o cluster cuida disso.

Ideia-chave: Você não fala mais com servidores um por um. Você fala com o cluster, e ele distribui o trabalho.

kubectl get nodes

Passo 2 · ConceitoGerência e cozinha

Pense num restaurante. Na cozinha, os cozinheiros preparam os pratos. Na gerência, alguém recebe os pedidos, anota tudo e decide quem faz o quê.

No cluster é igual: os nodes são a cozinha, onde as aplicações rodam de verdade. O control plane é a gerência: não cozinha nada, só toma decisões.

Bom saber: Em serviços de nuvem como EKS (Amazon), GKE (Google) e AKS (Microsoft), o provedor cuida da gerência para você. Você só vê, e paga, os nodes.

Passo 3 · ConceitoAPI server: o balcão de pedidos

Todo pedido ao cluster passa por um único balcão: o API server. Quando você digita um comando no kubectl, o programa de linha de comando do Kubernetes, ele manda uma requisição para esse balcão.

Os outros componentes também não conversam entre si diretamente: todos leem e escrevem pelo balcão. Assim existe um só ponto de verdade e de controle de acesso.

Ideia-chave: O kubectl é o cardápio que você usa; o API server é o balcão que recebe o pedido, confere se você tem permissão e anota.

kubectl get pods

Passo 4 · Conceitoetcd: o caderno da gerência

Tudo que o balcão aceita é anotado num caderno chamado etcd: quais apps existem, quantas cópias de cada uma, quais configurações. É a memória do cluster.

Para não perder anotações, o etcd guarda cópias em 3 ou 5 máquinas e só confirma uma escrita quando a maioria concorda. Isso se chama consenso.

Atenção: Se o etcd se perde sem backup, o cluster esquece tudo o que deveria estar rodando. Fazer backup dele é obrigação de quem cuida do próprio control plane.

Passo 5 · ConceitoScheduler: quem escala a equipe

Chegou um pod novo e ninguém disse onde ele deve rodar. Quem decide é o scheduler (agendador).

Ele faz duas rodadas. Primeiro elimina os nodes que não servem: sem memória livre, sem o hardware necessário, proibidos por alguma regra. Depois dá nota aos que sobraram e escolhe o melhor, como um gerente que escala o cozinheiro mais folgado.

Bom saber: O scheduler só decide e anota a decisão. Quem realmente liga o pod é o node escolhido.

kubectl get pods -o wide

Passo 6 · ConceitoControllers: o fiscal que nunca dorme

Os controllers são vários pequenos fiscais. Cada um vigia um tipo de coisa e compara o que deveria existir com o que existe de fato.

Se o caderno diz “quero 4 pods da API” e só existem 2, o fiscal cria mais 2. Se existissem 5, ele apagaria 1. Esse ciclo de olhar, comparar e corrigir se chama reconciliação.

Ideia-chave: Desejado diferente do real: o controller age. Desejado igual ao real: nada acontece. Esse ciclo roda o tempo todo, para sempre.

Passo 7 · Conceitokubelet: o encarregado de cada máquina

Cada node tem um encarregado chamado kubelet. Ele pergunta ao API server quais pods devem rodar na sua máquina e garante que estejam de pé.

Ele também faz health checks: de tempos em tempos, “cutuca” cada container para saber se está vivo e respondendo. Se um não responde, ele reinicia.

Bom saber: Os anéis verdes no diagrama são health checks: pequenas perguntas do tipo “tudo bem aí?”.

kubectl describe node node-1

Passo 8 · ConceitoContainer runtime: quem liga os containers

Para ligar um container, o node precisa da imagem, a receita. Ele baixa a imagem de um registry: um depósito de imagens como o Docker Hub ou o da sua empresa.

Quem faz o trabalho pesado de baixar e rodar é o container runtime, geralmente o containerd. O kubelet só dá a ordem.

Atenção: Baixar uma imagem grande pode levar dezenas de segundos. Imagens enxutas fazem o cluster reagir mais rápido.

Passo 9 · ConceitoTodo pod tem seu endereço

Cada pod ganha um endereço IP próprio, como um ramal de telefone interno. Um pod pode ligar para outro em qualquer node, sem saber em que máquina ele está.

Quem monta esse encanamento é a rede do cluster, com ajuda do kube-proxy em cada node. Para você, parece que todos os pods estão na mesma sala.

Ideia-chave: Endereços de pod mudam quando um pod é recriado. Na lição de Service você vai ver como resolver isso com um nome fixo.

Passo 10 · Trade-offTrade-off: e se a gerência cair?

O API server parou. Curiosamente, a loja continua no ar: os pods que já estavam rodando seguem atendendo, porque os nodes não dependem da gerência para trabalhar.

Mas ninguém consegue mudar nada: não dá para atualizar, escalar ou recuperar um pod que morrer. Por isso, em produção, o control plane roda em 3 cópias.

Atenção: Control plane fora não derruba o app na hora, mas deixa o cluster sem ninguém para corrigir problemas.

Passo 11 · ResumoResumo: quem faz o quê

A gerência decide, a cozinha executa, e toda comunicação passa pelo balcão.

Bom saber: Se você usa um Kubernetes gerenciado, raramente vai mexer no control plane. Mas saber quem faz o quê ajuda muito a encontrar problemas.

PeçaOnde ficaFaz o quê
API serverControl planeRecebe e confere todo pedido
etcdControl planeGuarda o estado do cluster
schedulerControl planeEscolhe o node de cada pod
controllersControl planeCorrigem desejado × real
kubeletCada nodeLiga e vigia os pods
runtimeCada nodeBaixa imagens e roda containers
