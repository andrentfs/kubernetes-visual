ConfigMaps, Secrets e SecurityContext

Tirar configuração e senhas de dentro da imagem, e rodar containers com o mínimo de poder.

Você vai aprender

  • Separar configuração da imagem com ConfigMap
  • Escolher entre variável de ambiente e arquivo

  • Barrar pods inseguros com Pod Security

Passo a passo

Passo 1 · ProblemaConfiguração presa dentro da imagem

O endereço do banco foi escrito direto no código da API: DB_HOST=prod-db. Para rodar a mesma API em homologação, a equipe precisa gerar outra imagem.

Uma imagem por ambiente é lenta e arriscada: a imagem que você testou não é a mesma que vai para produção.

Atenção: A regra dos apps modernos: a mesma imagem em todo lugar, só a configuração muda.

Passo 2 · SoluçãoConfigMap: a configuração fora da imagem

Um ConfigMap é um objeto do Kubernetes que guarda pares chave-valor ou arquivos inteiros de configuração, como DB_HOST=db.

Os pods leem o ConfigMap ao ligar. Para outro ambiente, basta outro ConfigMap com o mesmo nome em outro namespace; a imagem é a mesma.

Ideia-chave: ConfigMap é para dados que não são segredo. Limite de 1 MiB por objeto.

kubectl create configmap loja-config --from-literal=DB_HOST=db

Passo 3 · ConceitoDuas formas de entregar: variável ou arquivo

Como variável de ambiente: env com valueFrom.configMapKeyRef (uma chave) ou envFrom (todas as chaves de uma vez).

Como arquivo: um volume do tipo configMap montado numa pasta, por exemplo /etc/config. Cada chave vira um arquivo dentro dela.

Bom saber: Use env para valores curtos (portas, URLs) e volume para arquivos inteiros (nginx.conf, application.yaml).

Passo 4 · Trade-offTrade-off: quem vê a mudança?

Você mudou o ConfigMap. O pod que recebeu como volume vê o arquivo novo em até um minuto, sozinho.

O pod que recebeu como variável de ambiente continua com o valor antigo: variáveis só são lidas quando o container liga. Precisa reiniciar.

Atenção: Montagem com subPath também não atualiza sozinha. Na dúvida, kubectl rollout restart.

kubectl rollout restart deployment/api

Passo 5 · SoluçãoSecret: para senhas e chaves

Senhas, tokens e certificados vão num Secret. Ele funciona quase igual ao ConfigMap: env ou volume.

A diferença é o tratamento: o RBAC pode separar quem lê Secrets, o kubelet guarda os volumes de Secret em memória (tmpfs) no node, e dá para criptografar no etcd.

Atenção: Por padrão o valor só fica em base64. echo … | base64 -d mostra a senha. Não é criptografia.

kubectl create secret generic db-cred --from-literal=password=s3nh4

Passo 6 · ConceitoTipos de Secret

Opaque é o genérico, para qualquer chave-valor. kubernetes.io/tls guarda certificado e chave (usado pelo Ingress para HTTPS).

kubernetes.io/dockerconfigjson guarda o login de um registry privado. O pod usa esse Secret em imagePullSecrets para conseguir baixar a imagem.

TipoComo criar
Opaquecreate secret generic
TLScreate secret tls
Registrycreate secret docker-registry
kubectl create secret tls loja-tls --cert=tls.crt --key=tls.key

Passo 7 · ProblemaContainer rodando como root

Por padrão, muitas imagens rodam como root (usuário 0). Se alguém invadir o app por uma falha, já começa com o máximo de poder dentro do container.

Combinado com outros erros (volume do node montado, container privilegiado), o invasor pode chegar ao próprio node.

Atenção: Root no container é um degrau a menos entre uma falha no app e o controle da máquina.

Passo 8 · SoluçãoSecurityContext: rodar com menos poder

O securityContext define como o container roda. runAsNonRoot: true recusa iniciar como root; runAsUser: 1000 escolhe o usuário.

readOnlyRootFilesystem: true impede escrever no disco do container, e allowPrivilegeEscalation: false impede ganhar mais poder depois de ligado.

Ideia-chave: O securityContext pode ir no pod (vale para todos os containers) ou em cada container (sobrepõe o do pod).

Passo 9 · ConceitoCapabilities: poderes avulsos

No Linux, os poderes do root são divididos em capabilities: abrir portas abaixo de 1024, mudar a rede, mudar dono de arquivos…

O mais seguro é capabilities.drop: ["ALL"] e devolver só o necessário, como add: ["NET_BIND_SERVICE"] para escutar na porta 80.

Bom saber: privileged: true liga todas as capabilities e quase tudo do node. Evite, a não ser em agentes de sistema muito específicos.

Passo 10 · ConceitoPod Security: o porteiro do namespace

Para não depender de cada time lembrar do securityContext, o admission controller Pod Security aplica regras por namespace.

Com a label pod-security.kubernetes.io/enforce=restricted, o API server recusa pods que rodam como root, que pedem privilégios ou que não derrubam capabilities.

NívelO que exige
privilegedNada, tudo liberado
baselineBloqueia o mais perigoso
restrictedBoas práticas completas
kubectl label ns loja pod-security.kubernetes.io/enforce=restricted

Passo 11 · ResumoResumo: configuração e segurança do pod

A imagem é a mesma em todo lugar; o que muda vem de ConfigMaps e Secrets, e o container roda com o mínimo de poder.
