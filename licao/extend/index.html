Extensões: CRI, CNI, CSI, CRDs e Operators

O Kubernetes é uma plataforma: plugins de runtime, rede e disco, e novos tipos de objeto com seus próprios controladores.

12 minIntermediário10 passos

Esta é a versão em texto. A lição interativa tem o diagrama animado de cada passo.

Você vai aprender

  • Conhecer as interfaces CRI, CNI e CSI
  • Entender o que é uma CRD
  • Entender o padrão Operator
  • Instalar e explorar operadores

Passo a passo

Passo 1 · ContextoTrês tomadas padronizadas

O kubelet não sabe rodar containers, montar rede nem criar discos sozinho. Ele conversa com plugins por três interfaces padronizadas.

CRI para o runtime de containers, CNI para a rede dos pods, CSI para o armazenamento. Qualquer plugin que siga a interface encaixa.

Ideia-chave: É como uma tomada: o Kubernetes define o formato, e cada fornecedor faz o seu plugue.

Passo 2 · ConceitoCRI: o runtime de containers

Container Runtime Interface. O kubelet pede “crie este container” e o runtime faz: containerd ou CRI-O são os mais comuns.

No node, crictl fala direto com o runtime pela CRI: ps, logs, images, inspect. Útil quando o kubectl não ajuda.

Bom saber: O Docker Engine não fala CRI direto; desde a versão 1.24 o Kubernetes usa containerd ou CRI-O.

crictl ps

Passo 3 · ConceitoCSI: os drivers de disco

Container Storage Interface. Cada provedor de armazenamento (EBS na AWS, Persistent Disk no GCP, Ceph…) publica um driver CSI.

A StorageClass indica o driver no campo provisioner, e ele cria, conecta e expande os discos.

kubectl get csidrivers

Passo 4 · ConceitoCNI: a rede, de novo

Container Network Interface, que você já viu na lição de rede. Quando um pod nasce, o runtime chama o plugin CNI para dar IP e ligar o pod à rede.

A configuração fica em /etc/cni/net.d; os binários, em /opt/cni/bin.

ls /etc/cni/net.d

Passo 5 · ConceitoCRD: ensinando um tipo novo ao Kubernetes

Uma CustomResourceDefinition acrescenta um tipo novo à API, como Database. Depois de aplicada, o API server aceita objetos desse tipo e o kubectl passa a conhecê-los.

A CRD define o nome, o grupo (como loja.com/v1) e o esquema dos campos.

kubectl apply -f database-crd.yaml

Passo 6 · ConceitoUm objeto do tipo novo

Agora você cria um Database chamado loja-db com replicas: 3 e storage: 20Gi. Ele fica salvo no etcd como qualquer outro objeto.

Mas, sozinho, nada acontece: nenhum pod nasce. A CRD só ensinou o formato; falta alguém que saiba agir.

Atenção: CRD sem controlador é só um formulário guardado.

kubectl get databases

Passo 7 · ConceitoOperator: o especialista automatizado

Um Operator é um controlador que vigia objetos do tipo novo e faz o trabalho: vê o loja-db e cria um StatefulSet, Services, PVCs, configura réplicas e backups.

É o mesmo loop de reconciliação dos controllers nativos, com o conhecimento de um especialista (um DBA, por exemplo) escrito em código.

Ideia-chave: CRD + controlador = Operator. Você declara “quero um banco com 3 réplicas” e ele cuida do resto.

Passo 8 · ConceitoInstalando um operador

Operadores normalmente vêm em charts do Helm ou manifestos prontos, que instalam as CRDs e o pod do operador juntos.

Exemplos comuns: cert-manager (certificados TLS), Prometheus Operator (monitoramento), operadores de bancos como CloudNativePG.

helm install cert-manager jetstack/cert-manager -n cert-manager --create-namespace --set crds.enabled=true

Passo 9 · ConceitoExplorando CRDs no cluster

kubectl get crd lista os tipos novos. kubectl api-resources mostra todos os tipos, nativos e personalizados, com nome curto e grupo.

kubectl explain também funciona com CRDs que têm esquema: kubectl explain certificate.spec.

kubectl get crd | grep cert-manager

Passo 10 · ResumoResumo: como o Kubernetes cresce

Interfaces padronizadas deixam trocar runtime, rede e disco. CRDs e Operators deixam a própria API crescer.
