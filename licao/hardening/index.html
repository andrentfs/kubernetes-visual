Passo a passo

Passo 1 · ContextoOnde um cluster pode ser atacado

Um cluster recém-instalado tem várias portas de entrada: o API server (6443), o etcd (2379), o kubelet de cada node (10250) e, na nuvem, o serviço de metadados da máquina (169.254.169.254).

A CKS cobra exatamente isto: revisar cada uma dessas entradas e deixar aberto só o necessário, sempre com autenticação.

Ideia-chave: Segurança no Kubernetes é em camadas: control plane, nodes, rede, imagens e o que roda dentro dos containers.

Passo 2 · Conceitokube-bench: o CIS Benchmark automatizado

O CIS Benchmark do Kubernetes é uma lista de recomendações para o control plane, o etcd, os nodes e as políticas. O kube-bench roda essas verificações e marca cada item como PASS, FAIL, WARN ou INFO.

kube-bench run --targets master confere o control plane; --targets node confere os nodes. Para cada FAIL, ele mostra a correção sugerida (remediation).

Atenção: A numeração dos itens muda entre versões do benchmark. Na prova, procure o item citado na tarefa e siga a correção que o próprio kube-bench mostra.

kube-bench run --targets master

Passo 3 · SoluçãoCorrigindo um item que falhou

Quase toda correção é uma flag no manifesto de um pod estático, em /etc/kubernetes/manifests, ou um campo no config do kubelet (/var/lib/kubelet/config.yaml, seguido de systemctl restart kubelet).

Exemplo comum: --profiling=false no kube-apiserver. Ao salvar o manifesto, o kubelet recria o pod sozinho. Rode o kube-bench de novo para ver o PASS.

vi /etc/kubernetes/manifests/kube-apiserver.yaml

Passo 4 · ProblemaQuando a edição derruba a API

Um erro de digitação no manifesto e o kube-apiserver não sobe: o kubectl para de responder com connection refused.

Sem API, investigue direto no node: crictl ps -a mostra o container que saiu, e os logs ficam em /var/log/pods ou em crictl logs <id>.

Atenção: Antes de editar, copie o manifesto para fora da pasta (por exemplo, /root). O kubelet lê os arquivos dessa pasta, e um backup lá dentro pode virar um segundo pod.

crictl ps -a | grep kube-apiserver

Passo 5 · ConceitoQuem pode falar com o API server

Requisições sem credencial viram o usuário system:anonymous. Confira se nenhum RoleBinding ou ClusterRoleBinding dá permissões a system:anonymous ou ao grupo system:unauthenticated.

No kube-apiserver, --authorization-mode=Node,RBAC e o admission plugin NodeRestriction fazem cada kubelet só mexer no próprio Node e nos pods dele.

Ideia-chave: O kubelet também tem uma API (porta 10250). No config dele: authentication.anonymous.enabled: false e authorization.mode: Webhook.

Passo 6 · SoluçãoServiceAccounts sem token desnecessário

Por padrão, todo pod recebe o token da sua ServiceAccount montado em /var/run/secrets/kubernetes.io/serviceaccount. Se o app não fala com a API, esse token só serve a um invasor.

Desligue com automountServiceAccountToken: false na ServiceAccount ou no pod. E crie uma ServiceAccount por app, com só as permissões que ele usa.

kubectl patch sa default -n loja -p '{"automountServiceAccountToken":false}'

Passo 7 · ProblemaO endpoint de metadados da nuvem

Em AWS, GCP e Azure, qualquer processo da máquina pode consultar 169.254.169.254 e receber dados da instância, às vezes até credenciais temporárias da nuvem.

Um pod invadido também alcança esse endereço, porque o tráfego dele sai pelo node.

Atenção: Com essas credenciais, o invasor sai do cluster e passa a agir na conta da nuvem.

kubectl exec app -- curl -s 169.254.169.254

Passo 8 · SoluçãoBloqueando os metadados com NetworkPolicy

Uma NetworkPolicy de egress libera ipBlock 0.0.0.0/0 com except: 169.254.169.254/32. O resto continua acessível; só o endpoint de metadados fica de fora.

Deixe fora dessa política só os pods que realmente precisam dos metadados, como agentes da própria nuvem.

kubectl apply -f deny-metadata.yaml

Passo 9 · SoluçãoIngress com TLS

O certificado e a chave ficam num Secret do tipo kubernetes.io/tls: kubectl create secret tls loja-tls --cert=tls.crt --key=tls.key.

No Ingress, spec.tls lista os hosts e o secretName. O controller passa a servir HTTPS com esse certificado.

Atenção: O host em spec.tls precisa bater com o das regras e com o do certificado. Se não bater, muitos controllers servem um certificado padrão.

kubectl create secret tls loja-tls --cert=tls.crt --key=tls.key

Passo 10 · ConceitoVerificando os binários da plataforma

Antes de instalar ou atualizar, confira se kubelet, kubeadm e kubectl são os oficiais. O projeto publica os hashes: o CHANGELOG de cada versão traz o SHA512 dos pacotes, e dl.k8s.io tem o arquivo de hash ao lado de cada binário.

Calcule com sha512sum (ou sha256sum) e compare com o publicado para a sua versão e arquitetura. Valor diferente: não use.

sha512sum /usr/bin/kubelet

Revise o cluster com o kube-bench e corrija camada por camada, sempre com backup do que for editar.
