Helm e Kustomize

Instalar e reaproveitar aplicações inteiras sem copiar YAML para cada ambiente.

Esta é a versão em texto. A lição interativa tem o diagrama animado de cada passo.

Você vai aprender

  • Entender o problema de copiar YAML
  • Instalar um chart com Helm
  • Personalizar com values
  • Atualizar e voltar versões com Helm
  • Montar base e overlays com Kustomize

Passo a passo

Passo 1 · ProblemaUm YAML por ambiente

A loja tem dev, homologação e produção. A equipe mantém três cópias dos manifestos, mudando à mão número de réplicas, imagem e domínio.

Uma correção feita em produção e esquecida em dev é questão de tempo. E instalar algo pronto, como um NGINX completo, exigiria escrever dezenas de arquivos.

Atenção: Cópia de YAML é dívida: cada mudança precisa ser repetida em todo lugar.

Passo 2 · ConceitoHelm: o gerenciador de pacotes

Helm empacota uma aplicação num chart: modelos de YAML (templates/) com variáveis, e um arquivo values.yaml com os valores padrão.

Charts ficam em repositórios, como pacotes de um sistema operacional. helm repo add registra um repositório e helm search repo procura charts.

Ideia-chave: Chart é a receita; release é cada instalação dela no cluster, com nome próprio.

Passo 3 · Soluçãohelm install

helm install loja bitnami/nginx -n loja instala o chart com o nome de release “loja”. O Helm gera os YAML, aplica no cluster e guarda a revisão 1.

helm list -A mostra todos os releases de todos os namespaces, com versão do chart e status.

helm install loja bitnami/nginx -n loja --create-namespace

Passo 4 · ConceitoPersonalizando com values

Você troca os valores padrão sem tocar no chart: --set replicaCount=3 na linha de comando, ou -f values-prod.yaml com vários valores juntos.

helm show values bitnami/nginx lista todos os valores que o chart aceita.

Bom saber: Um arquivo de values por ambiente substitui as três cópias de YAML: o chart é o mesmo.

helm upgrade loja bitnami/nginx --set replicaCount=3 -f values-prod.yaml

Passo 5 · Conceitohelm upgrade e rollback

helm upgrade aplica valores ou versão nova do chart e cria uma revisão nova. helm history mostra todas as revisões.

Deu errado? helm rollback loja 1 volta para a revisão 1. O Helm reaplica o que tinha naquela revisão.

helm history loja && helm rollback loja 1

Passo 6 · ConceitoOlhar antes de aplicar

helm template gera os YAML sem instalar nada. Ótimo para revisar ou guardar num arquivo.

helm uninstall loja remove tudo que o release criou. --dry-run mostra o que o install ou upgrade faria.

helm template loja bitnami/nginx > out.yaml

Passo 7 · ConceitoKustomize: base e overlays

O Kustomize segue outro caminho: sem templates. Você escreve o YAML normal numa pasta base/ e cria overlays/ para cada ambiente, que descrevem só as diferenças.

Ele já vem embutido no kubectl: não precisa instalar nada.

Ideia-chave: Helm usa variáveis em modelos. Kustomize aplica ajustes em cima de YAML comum.

Passo 8 · ConceitoO arquivo kustomization.yaml

Cada pasta tem um kustomization.yaml. Na base, ele lista os arquivos (resources). No overlay, aponta para a base e adiciona ajustes.

Ajustes comuns: namePrefix (prod-), namespace, images (troca a tag da imagem), replicas e patches (pedaços de YAML que sobrescrevem campos).

Passo 9 · Soluçãokubectl apply -k

kubectl apply -k overlays/prod junta a base com os ajustes do overlay e aplica no cluster. kubectl kustomize overlays/prod só mostra o resultado.

Os pods de produção ganham o prefixo prod- e a imagem e o número de réplicas definidos no overlay.

kubectl apply -k overlays/prod

Passo 10 · ResumoResumo: Helm ou Kustomize?

Use Helm para instalar software de terceiros e para pacotes com muitas opções. Use Kustomize para variar seus próprios manifestos por ambiente.
