Passo a passo

Passo 1 · ContextoDois times, um cluster

Os times A e B dividem o cluster, cada um no seu namespace. Os dois guardam senhas em Secrets, que o API server grava no etcd.

A pergunta da CKS é: quem consegue ler essas senhas, e quanto um time consegue afetar o outro?

Passo 2 · ProblemaSecret é base64, não criptografia

Por padrão, o API server grava os Secrets no etcd sem criptografia. Quem tem acesso ao etcd, ou a um backup dele, lê a senha direto: etcdctl get /registry/secrets/loja/db-pass.

O base64 do YAML é só codificação: base64 -d devolve o texto original.

Atenção: Na prova, o etcdctl precisa dos certificados: --cacert, --cert e --key. Os caminhos estão no manifesto do etcd.

etcdctl get /registry/secrets/loja/db-pass

Passo 3 · SoluçãoCriptografia em repouso

Crie um EncryptionConfiguration com os resources (secrets) e os providers em ordem. O primeiro provider é o usado para gravar: aescbc, aesgcm, secretbox ou kms. identity (sem criptografia) vai por último, só para ler o que já existe.

No kube-apiserver: --encryption-provider-config apontando para o arquivo, com volume e volumeMount. Os Secrets novos aparecem no etcd com o prefixo k8s:enc:aescbc:v1:.

Bom saber: Em produção, a documentação recomenda o provider kms (v2), com a chave fora do cluster.

grep encryption-provider-config /etc/kubernetes/manifests/kube-apiserver.yaml

Passo 4 · ConceitoCriptografando o que já existia

A configuração só vale para gravações novas. Secrets antigos continuam em texto puro até serem regravados.

kubectl get secrets -A -o json | kubectl replace -f - regrava todos. Depois, confira no etcd que todos têm o prefixo k8s:enc.

kubectl get secrets -A -o json | kubectl replace -f -

Passo 5 · ConceitoQuem pode ler os Secrets

Criptografar o etcd não protege contra quem tem get secrets na API. Dê get e list em secrets só a quem precisa, e num namespace só. Lembre que list também devolve o conteúdo.

No pod, prefira montar o Secret como volume em vez de variáveis de ambiente: variáveis vazam mais fácil em logs, dumps e processos filhos.

Ideia-chave: Quem pode criar pods num namespace pode montar qualquer Secret dele. Isso também é acesso aos Secrets.

Passo 6 · ConceitoIsolando os times

Um namespace sozinho não isola nada. Junte RBAC por namespace, NetworkPolicy de default deny entre namespaces, ResourceQuota e LimitRange para um time não esgotar o cluster, e Pod Security Standards (label enforce=restricted).

Para isolamento mais forte, separe os nodes por time com taints e nodeSelector, ou use clusters diferentes.

kubectl label ns tenant-a pod-security.kubernetes.io/enforce=restricted

Passo 7 · ProblemaTodos dividem o mesmo kernel

Containers são processos no mesmo kernel do node. Uma falha no kernel (container escape) pode levar um pod aos outros pods do mesmo node, inclusive de outros times.

Para código pouco confiável, como builds de clientes ou plugins de terceiros, esse risco é alto demais.

Passo 8 · SoluçãoSandbox com RuntimeClass

Runtimes como o gVisor (runsc) e o Kata Containers põem uma camada entre o container e o kernel do node: um kernel em espaço de usuário ou uma VM leve.

Uma RuntimeClass com handler: runsc aponta para o runtime instalado no node. No pod, runtimeClassName: gvisor. Os outros pods continuam no runtime normal.

Atenção: O handler precisa existir na configuração do containerd de cada node, senão o pod não sobe.

kubectl get runtimeclass

Passo 9 · ConceitoTráfego cifrado entre pods (mTLS)

Por padrão, o tráfego entre pods não é criptografado: quem captura pacotes na rede vê o conteúdo.

Um service mesh como o Istio põe mTLS entre os pods (no Istio, PeerAuthentication com mode: STRICT). O Cilium pode cifrar o tráfego entre nodes com WireGuard ou IPsec, sem mudar os pods.

Passo 10 · Trade-offTrade-off: cada camada tem custo

O mesh adiciona um proxy (sidecar ou por node), latência e mais um componente para operar. O sandbox deixa algumas chamadas mais lentas, e nem todo app é compatível.

Use onde o risco justifica: dados sensíveis, multi-tenancy de verdade, código de terceiros.

Passo 11 · ResumoResumo: dados protegidos, times separados

Cada risco tem uma camada própria; combine as que fazem sentido para o seu cluster.
