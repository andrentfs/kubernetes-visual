Instalar e manter o cluster com kubeadm

Do zero a um cluster funcionando: preparar as máquinas, kubeadm init e join, upgrades, backup do etcd, alta disponibilidade e certificados.

15 minIntermediário13 passos

▶ Abrir a lição interativa

Esta é a versão em texto. A lição interativa tem o diagrama animado de cada passo.

Você vai aprender

  • Preparar os nodes para o Kubernetes
  • Criar o cluster com kubeadm init e join
  • Usar kubeconfig e contextos
  • Atualizar o cluster uma versão por vez
  • Fazer backup e restore do etcd
  • Entender HA e certificados

Passo a passo

Passo 1 · ContextoPreparando as máquinas

Antes do Kubernetes, cada máquina precisa de um container runtime (containerd), dos pacotes kubeadm, kubelet e kubectl, e de alguns ajustes de Linux.

Os ajustes clássicos: desligar o swap, carregar os módulos overlay e br_netfilter, e ligar net.ipv4.ip_forward=1. O kubelet fica rodando, mas esperando ordens.

Atenção: Versões do kubeadm, do kubelet e do control plane precisam ser compatíveis. Instale a mesma versão menor nos três.

Passo 2 · Soluçãokubeadm init: nasce o control plane

No primeiro node, kubeadm init cria tudo: os certificados em /etc/kubernetes/pki, os manifestos dos static pods (etcd, API server, scheduler, controller-manager) e o arquivo admin.conf.

No fim ele imprime dois comandos: como copiar o admin.conf para ~/.kube/config e o kubeadm join que os workers vão usar.

Bom saber: --pod-network-cidr define a faixa de IPs dos pods. Precisa combinar com o plugin de rede que você vai instalar.

kubeadm init --pod-network-cidr=10.244.0.0/16

Passo 3 · ProblemaNode NotReady e CoreDNS parado

Logo depois do init, o node aparece NotReady e os pods do CoreDNS ficam Pending. Não é erro: falta o plugin de rede (CNI).

O Kubernetes não traz rede própria. Sem um CNI, os pods não ganham IP e o node não é considerado pronto.

Passo 4 · SoluçãoInstalando o plugin de rede

Você aplica um CNI, como Calico, Cilium ou Flannel, normalmente com um único kubectl apply. Ele roda um pod em cada node.

Com a rede pronta, o node fica Ready e o CoreDNS sobe.

kubectl apply -f calico.yaml

Passo 5 · Soluçãokubeadm join: chegam os workers

Em cada worker, o comando kubeadm join com o endereço do API server, um token e o hash do certificado faz o node entrar no cluster.

O token expira em 24 horas. Para gerar outro comando completo: kubeadm token create --print-join-command.

kubeadm token create --print-join-command

Passo 6 · Conceitokubeconfig e contextos

O arquivo ~/.kube/config tem três listas: clusters (endereços), users (credenciais) e contexts (qual usuário em qual cluster e namespace).

kubectl config get-contexts lista, use-context troca, e set-context --current --namespace=app muda o namespace padrão.

Atenção: No exame, cada questão começa com um comando de use-context. Pular esse passo é o erro mais comum.

kubectl config use-context prod

Passo 7 · ConceitoUpgrade: uma versão menor por vez

Não dá para pular versões: de 1.35 vai para 1.36, depois 1.37. Primeiro o control plane, depois os workers.

No control plane: atualize o pacote kubeadm, rode kubeadm upgrade plan para ver as opções e kubeadm upgrade apply v1.36.0.

kubeadm upgrade plan

Passo 8 · SoluçãoUpgrade dos workers, um por vez

Para cada worker: kubectl drain para tirar os pods, atualizar o pacote kubeadm, rodar kubeadm upgrade node, atualizar kubelet e kubectl, systemctl daemon-reload e restart kubelet.

No fim, kubectl uncordon devolve o node ao trabalho. No control plane, o mesmo vale para o kubelet: drain, atualizar, reiniciar, uncordon.

Ideia-chave: Ordem que cai na prova: drain → kubeadm → kubeadm upgrade → kubelet/kubectl → restart → uncordon.

kubeadm upgrade apply v1.36.0

Passo 9 · SoluçãoBackup do etcd

O etcd guarda o cluster inteiro. Um snapshot salva tudo num arquivo: etcdctl snapshot save /opt/backup.db.

O etcdctl precisa do endereço e dos certificados: --endpoints=https://127.0.0.1:2379, --cacert, --cert e --key, que ficam em /etc/kubernetes/pki/etcd. O manifesto do etcd mostra os caminhos.

Atenção: Sem os três certificados, o etcdctl falha com erro de conexão. Copie os caminhos de /etc/kubernetes/manifests/etcd.yaml.

ETCDCTL_API=3 etcdctl snapshot save /opt/backup.db

Passo 10 · SoluçãoRestore do etcd

etcdctl snapshot restore cria uma pasta de dados nova a partir do arquivo, com --data-dir /var/lib/etcd-restore.

Depois, edite o manifesto do etcd para o volume hostPath apontar para a pasta nova. O kubelet religa o etcd com os dados restaurados.

Bom saber: Em versões recentes, o restore também pode ser feito com etcdutl. O conceito é o mesmo: nova pasta e apontar o manifesto.

etcdctl snapshot restore /opt/backup.db --data-dir /var/lib/etcd-restore

Passo 11 · ConceitoControl plane de alta disponibilidade

Com um só control plane, perder aquela máquina deixa o cluster sem gerência. Em produção usam-se 3 (ou 5) control planes atrás de um load balancer na porta 6443.

O etcd pode ficar empilhado (stacked, um em cada control plane) ou externo, em máquinas só dele. Número ímpar, por causa do consenso.

Bom saber: Com kubeadm: init com --control-plane-endpoint apontando para o load balancer e join --control-plane nos outros.

Passo 12 · ConceitoCertificados do cluster

O kubeadm cria certificados que valem 1 ano. kubeadm certs check-expiration mostra as datas e kubeadm certs renew all renova; um upgrade também renova.

Para dar acesso a uma pessoa, ela gera uma chave e um CertificateSigningRequest; um admin aprova com kubectl certificate approve.

Atenção: Certificado vencido derruba o acesso ao cluster de uma vez. Monitore as datas.

kubeadm certs check-expiration

Passo 13 · ResumoResumo: o ciclo de vida do cluster

Preparar, init, CNI, join; depois manter: upgrade versão por versão, backup do etcd e certificados em dia.
