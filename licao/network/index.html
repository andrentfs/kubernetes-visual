Rede do cluster: CNI, Services e CoreDNS

Como os pods se encontram: o modelo de rede, os tipos de Service, o DNS do cluster e a Gateway API.

Passo a passo

Passo 1 · ContextoA regra de ouro da rede

No Kubernetes, todo pod ganha um IP próprio, e qualquer pod fala com qualquer outro pod pelo IP, em qualquer node, sem tradução de endereço (NAT).

É como se todos os pods estivessem na mesma rede local, mesmo espalhados por máquinas diferentes.

Ideia-chave: Pod com IP, todos se alcançam, sem NAT. Por padrão, também não há bloqueio: isso é papel da NetworkPolicy.

Passo 2 · ConceitoCNI: quem monta a rede

O Kubernetes define a regra, mas não implementa a rede. Quem faz isso é um plugin CNI (Container Network Interface): Calico, Cilium, Flannel…

Ele roda em cada node (um DaemonSet), dá IP para cada pod novo e cria as rotas entre os nodes.

Bom saber: A configuração do CNI fica em /etc/cni/net.d e os binários em /opt/cni/bin. É onde olhar se pods não ganham IP.

Passo 3 · Conceitokube-proxy: o Service de verdade

O IP de um Service é virtual: nenhuma interface de rede tem esse endereço. Em cada node, o kube-proxy cria regras (iptables ou IPVS) que trocam o IP do Service pelo IP de um pod real.

Por isso o Service funciona em qualquer node: as regras estão em todos.

Bom saber: Alguns CNIs, como o Cilium, podem substituir o kube-proxy usando eBPF.

Passo 4 · ConceitoClusterIP: só dentro do cluster

O tipo padrão. O Service ganha um IP virtual (como 10.96.0.20) e um nome DNS, acessíveis só de dentro do cluster.

port é a porta do Service; targetPort é a porta do container. Elas podem ser diferentes: 80 no Service, 8080 no app.

Atenção: Quem está fora do cluster não alcança um ClusterIP. Para isso, NodePort, LoadBalancer, Ingress ou Gateway.

kubectl expose deploy api --port=80 --target-port=8080

Passo 5 · ConceitoNodePort: uma porta em cada node

O NodePort abre a mesma porta (entre 30000 e 32767) em todos os nodes. Quem acessar qualquer node nessa porta chega ao Service.

Ele inclui um ClusterIP por baixo. Bom para testes e laboratórios; em produção costuma ficar atrás de um balanceador.

kubectl expose deploy api --type=NodePort --port=80

Passo 6 · ConceitoLoadBalancer: o balanceador da nuvem

Em nuvens como AWS, GCP e Azure, um Service LoadBalancer pede ao provedor um balanceador externo com IP público, que manda o tráfego para os nodes.

Por baixo, ele cria um NodePort e um ClusterIP. Em clusters locais, sem provedor, o IP externo fica <pending> até instalar algo como o MetalLB.

Passo 7 · ConceitoEndpoints e Services headless

Atrás de todo Service há uma lista de endpoints (hoje em EndpointSlices) com os IPs dos pods prontos.

Um Service headless (clusterIP: None) não tem IP virtual: o DNS devolve direto os IPs dos pods. É usado com StatefulSets, onde cada réplica tem nome próprio (db-0, db-1…).

Passo 8 · ConceitoCoreDNS: os nomes do cluster

O CoreDNS roda em kube-system e responde os nomes do cluster. Um Service vira api.loja.svc.cluster.local.

Dentro do mesmo namespace basta “api”; de outro namespace, “api.loja”. O arquivo /etc/resolv.conf de cada pod já aponta para o CoreDNS.

De ondeNome que funciona
Mesmo namespaceapi
Outro namespaceapi.loja
Nome completoapi.loja.svc.cluster.local
kubectl run t --image=busybox --rm -it -- nslookup api.loja

Passo 9 · ProblemaQuando o DNS falha

Pods com timeout ou NXDOMAIN ao chamar outros serviços? Teste com um pod temporário: kubectl run t --image=busybox --rm -it -- nslookup api.loja.

Se nem kubernetes.default resolve, olhe os pods do CoreDNS (kubectl -n kube-system get pods -l k8s-app=kube-dns), os logs e o ConfigMap coredns.

Atenção: Se o nome não resolve mas o IP do Service funciona, o problema é DNS. Se nem o IP funciona, é Service ou rede.

kubectl -n kube-system logs -l k8s-app=kube-dns

Passo 10 · ConceitoGateway API: o sucessor do Ingress

A Gateway API divide a entrada em papéis. A GatewayClass diz qual implementação usar; o Gateway define onde escutar (porta, domínio, certificado); as rotas, como HTTPRoute, dizem para qual Service vai cada caminho.

Assim, o time de infraestrutura cuida do Gateway e cada time de app cria suas próprias rotas.

Bom saber: Ingress continua existindo e cai na prova também. A Gateway API é mais expressiva: pesos para canary, cabeçalhos, vários protocolos.

Passo 11 · ResumoResumo: como o tráfego chega ao pod

CNI dá IP aos pods, kube-proxy implementa os Services, CoreDNS dá nomes, e Ingress ou Gateway abrem a porta para fora.

TipoAlcance

NodePortPorta em cada node
LoadBalancerIP público da nuvem
