Quando um node cai

O que acontece, minuto a minuto, quando uma máquina do cluster some, e por que os pods não mudam de casa na hora.

12 minIntermediário12 passos

Esta é a versão em texto. A lição interativa tem o diagrama animado de cada passo.

Você vai aprender

  • Entender o batimento (heartbeat) dos nodes
  • Saber quanto tempo até o node virar NotReady
  • Entender os taints automáticos e os 5 minutos de tolerância
  • Ver por que StatefulSet e volumes travam
  • Destravar com o taint out-of-service

Passo a passo

Passo 1 · ContextoCada node avisa que está vivo

O cluster tem três nodes. A API roda com 3 réplicas, uma em cada node, e o banco (db-0, de um StatefulSet) roda no node-3, com o disco dele.

O kubelet de cada node manda um “estou vivo” para o API server a cada 10 segundos, renovando um objeto chamado Lease. No controller-manager, um controlador fica de olho nesses sinais: o node lifecycle controller.

Ideia-chave: O Kubernetes não enxerga as máquinas. Ele só sabe que um node está vivo porque o kubelet continua avisando.

Passo 2 · Problema0 s: a máquina apaga

A fonte do node-3 queimou. A máquina sumiu, junto com a réplica da API e o banco que rodavam nela.

Mas, para o cluster, nada mudou ainda: o node continua Ready e os pods continuam Running no kubectl. A única diferença é o silêncio: os avisos do node-3 pararam de chegar.

Atenção: Nos primeiros segundos, o kubectl mostra Running o que já não existe. Ele mostra o último estado conhecido, não o estado real.

kubectl get nodes

Passo 3 · Conceito50 s: o node vira NotReady

O controlador espera um prazo antes de desconfiar: o node-monitor-grace-period, de 50 segundos (era 40 s até a versão 1.31). Sem nenhum aviso nesse tempo, ele marca o node-3 como NotReady, com status Unknown.

Na mesma hora, ele marca os pods do node-3 como não prontos (Ready: False). Isso já tira esses pods dos endpoints dos Services: a partir daqui, nenhum cliente é mandado para o node morto.

Ideia-chave: O primeiro efeito de um node caído é no tráfego, não nos pods: em ~50 s o Service para de mandar clientes para lá.

Bom saber: Entre 0 e 50 s, parte das requisições ainda cai no node morto e falha. Retries no cliente ou no Ingress cobrem esse buraco.

kubectl get nodes

Passo 4 · ConceitoO node ganha uma placa de “interditado”

Junto com o NotReady, o controlador coloca dois taints no node-3: node.kubernetes.io/unreachable com o efeito NoSchedule, e o mesmo com o efeito NoExecute.

Taint é uma placa na porta do node. NoSchedule quer dizer “não coloque pods novos aqui”, e o scheduler passa a ignorar o node-3. NoExecute quer dizer “quem estiver aqui tem que sair”, mas só depois do prazo que cada pod tolera.

Bom saber: Se a máquina só perdeu a rede, os containers continuam rodando lá dentro, sem saber de nada. Por isso o Kubernetes é cauteloso antes de recriar pods em outro lugar.

kubectl describe node node-3

Passo 5 · ConceitoCada pod tolera 5 minutos

Todo pod ganha, sem você pedir, uma tolerância a esses taints: tolerationSeconds: 300. É como dizer “se o meu node sumir, eu espero 5 minutos antes de ir embora”.

O motivo: quedas curtas de rede são comuns. Se o Kubernetes recriasse tudo a cada piscada, um switch reiniciando faria metade do cluster mudar de lugar à toa.

Ideia-chave: Os pods do node caído só são despejados uns 5 minutos depois do NotReady. Somando tudo, a réplica nova aparece uns 5 min e 50 s depois da queda.

Bom saber: Dá para mudar por pod: uma tolerância para node.kubernetes.io/unreachable com tolerationSeconds: 30 faz o pod trocar de node bem mais rápido. Bom para apps sem estado; arriscado para bancos.

Passo 6 · Solução5 min 50 s: os pods são despejados

O prazo acabou. O controlador apaga os pods do node-3, que passam a aparecer como Terminating.

O ReplicaSet da API percebe que só tem 2 réplicas de verdade e cria uma nova. O scheduler escolhe o node-1, que tem espaço, e respeita o taint: o node-3 nem entra na conta. Em poucos segundos a API volta a ter 3 réplicas prontas.

kubectl get pods -o wide

Passo 7 · ConceitoO pod antigo fica Terminating

O pod antigo da API continua aparecendo como Terminating, e pode ficar assim por horas. Para ele sumir de vez, o kubelet do node-3 precisaria confirmar que parou o container, e ele não está lá para responder.

Para um Deployment, isso não importa: ele já criou a substituta e não conta pods que estão sendo apagados. O pod “zumbi” só ocupa uma linha no kubectl.

Atenção: Pods presos em Terminating num node NotReady são normais. Não é sinal de que o cluster travou.

Passo 8 · ProblemaO banco não volta sozinho

Com o db-0 é diferente. Um StatefulSet promete que nunca vão existir dois pods com o mesmo nome ao mesmo tempo. Enquanto o db-0 antigo estiver Terminating, ele não cria outro db-0.

E o cluster não tem como saber se a máquina morreu ou se só perdeu a rede, com o banco ainda gravando no disco. Criar um segundo db-0 poderia deixar dois bancos escrevendo nos mesmos dados.

Ideia-chave: Para Deployment, um node caído se resolve sozinho em uns 6 minutos. Para StatefulSet, alguém precisa confirmar que a máquina morreu de verdade.

kubectl get pods -l app=db

Passo 9 · ProblemaForçar a exclusão não basta

Muita gente força a exclusão: kubectl delete pod db-0 --force --grace-period=0. O pod antigo some do cluster e o StatefulSet cria o db-0 novo no node-2.

Só que o disco do banco (ReadWriteOnce) ainda consta como ligado ao node-3. O pod novo fica em ContainerCreating com o erro Multi-Attach, porque um volume RWO só pode estar ligado a um node por vez. O Kubernetes espera mais 6 minutos antes de soltar o disco à força.

Atenção: --force só apaga o registro no cluster, não desliga nada. Use só quando tiver certeza de que a máquina está desligada; senão, podem ficar dois bancos no mesmo disco.

kubectl delete pod db-0 --force --grace-period=0

Passo 10 · SoluçãoO jeito certo: avisar que o node morreu

Desde a versão 1.28 existe um jeito oficial: depois de confirmar que a máquina está desligada, você coloca no node o taint node.kubernetes.io/out-of-service.

É como dizer ao cluster “pode confiar, essa máquina não volta tão cedo”. O Kubernetes apaga na hora os pods presos, solta os volumes e deixa o StatefulSet recriar o db-0 em outro node, sem esperar os 6 minutos.

Bom saber: Em nuvem, quando a VM é apagada, o cloud controller manager costuma remover o objeto Node do cluster, e o efeito é parecido.

kubectl taint nodes node-3 node.kubernetes.io/out-of-service=nodeshutdown:NoExecute

Passo 11 · SoluçãoA máquina volta, mas fica vazia

A fonte foi trocada e o node-3 ligou de novo. O kubelet volta a mandar avisos, o node fica Ready e os taints unreachable saem sozinhos. O out-of-service, você tira à mão.

Os pods não voltam para o node-3: o Kubernetes não rebalanceia o que já está rodando. O node-3 só recebe pods novos daqui para a frente. Para redistribuir, use kubectl rollout restart ou uma ferramenta como o descheduler.

kubectl taint nodes node-3 node.kubernetes.io/out-of-service-

Passo 12 · ResumoResumo: a linha do tempo de um node caído

Quando um node cai, o Kubernetes primeiro desconfia, depois isola e só então recria. Cada etapa tem um prazo, e todos podem ser ajustados.

Para sofrer menos: tenha pelo menos 2 réplicas, espalhe as réplicas por nodes diferentes (topologySpreadConstraints ou anti-affinity) e use retries. Um PodDisruptionBudget não protege contra queda de máquina; ele vale só para saídas planejadas, como um drain.
