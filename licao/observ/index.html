Observabilidade e debug

Ver o que o app está fazendo: logs, eventos, métricas, comandos dentro do pod e as mudanças de API.

12 minIntermediário10 passos

▶ Abrir a lição interativa

Esta é a versão em texto. A lição interativa tem o diagrama animado de cada passo.

Você vai aprender

  • Ler logs, inclusive de containers específicos
  • Saber onde os logs ficam e como centralizar
  • Usar events e kubectl top
  • Depurar com exec, port-forward e debug
  • Formatar saídas com jsonpath e custom-columns
  • Lidar com APIs depreciadas

Passo a passo

Passo 1 · Contextokubectl logs: o que o app disse

Tudo que o container escreve na saída padrão (stdout e stderr) vira log. kubectl logs api-7d9 mostra; -f acompanha ao vivo; --tail=50 pega só o fim.

Para várias réplicas: kubectl logs -l app=api ou kubectl logs deploy/api (escolhe um pod do Deployment).

Ideia-chave: Apps em container devem escrever em stdout, não em arquivo. Assim o Kubernetes captura sem configuração extra.

kubectl logs -f deploy/api

Passo 2 · ConceitoPods com mais de um container

Se o pod tem mais de um container, kubectl logs pede para você escolher: -c app ou -c log. --all-containers=true junta tudo.

Init containers também têm logs. Se o pod está preso em Init, olhe o log do init container pelo nome.

kubectl logs api-7d9 -c log-shipper

Passo 3 · ConceitoOnde os logs moram

No node, o runtime grava os logs em /var/log/pods e o kubelet faz a rotação. Quando o pod é apagado, esses logs vão embora.

Para guardar e pesquisar, um agente como Fluent Bit roda em cada node (um DaemonSet), lê essa pasta e envia para um sistema central como Loki ou Elasticsearch.

Bom saber: kubectl logs só mostra o que ainda está no node. Histórico longo depende do sistema central.

Passo 4 · ConceitoEvents: o diário do cluster

O Kubernetes registra eventos: Scheduled, Pulling, Pulled, Started, BackOff, FailedScheduling. Eles aparecem no fim do describe e em kubectl get events.

Os eventos expiram depois de cerca de uma hora. Ordene por tempo com --sort-by=.lastTimestamp e filtre com --field-selector.

Atenção: Eventos são a primeira pista quando o log está vazio, como em ImagePullBackOff e Pending.

kubectl get events -A --sort-by=.lastTimestamp

Passo 5 · ConceitoMétricas: kubectl top

O metrics-server coleta CPU e memória de cada kubelet. Com ele instalado, kubectl top nodes e kubectl top pods mostram o consumo atual.

Use --sort-by=cpu ou memory para achar o pod mais pesado, e --containers para ver por container. O HPA usa essas mesmas métricas.

Bom saber: Sem metrics-server, kubectl top responde “Metrics API not available”.

kubectl top pods -A --sort-by=memory

Passo 6 · ConceitoEntrar no pod e abrir um túnel

kubectl exec -it api-7d9 -- sh abre um terminal dentro do container. Bom para ver arquivos, variáveis e testar conexões.

kubectl port-forward svc/api 8080:80 cria um túnel do seu computador para o Service. Você acessa localhost:8080 sem expor nada para fora.

kubectl port-forward svc/api 8080:80

Passo 7 · Conceitokubectl debug: quando o container não tem shell

Imagens mínimas (distroless) não têm sh nem ferramentas. O exec não ajuda.

kubectl debug adiciona um container efêmero ao pod, com a imagem que você quiser (busybox, netshoot), dividindo o processo e a rede do container alvo com --target.

Bom saber: kubectl debug node/node-1 -it --image=busybox abre um pod com acesso ao sistema do node, em /host.

kubectl debug -it api-7d9 --image=busybox --target=api

Passo 8 · ConceitoSaídas sob medida

-o wide mostra IP e node; -o yaml mostra o objeto inteiro. -o jsonpath='{.items[*].metadata.name}' extrai só o que você quer.

-o custom-columns monta uma tabela com as colunas que você escolher, e --sort-by ordena por qualquer campo.

Ideia-chave: O exame pede muito “salve a lista X no arquivo Y”. jsonpath e custom-columns resolvem rápido.

kubectl get pods -o custom-columns=NAME:.metadata.name,NODE:.spec.nodeName

Passo 9 · Trade-offTrade-off: APIs que saem de linha

Cada objeto tem uma apiVersion. Versões beta são substituídas e, depois de um aviso, removidas. Ingress em extensions/v1beta1 deixou de existir no 1.22; hoje é networking.k8s.io/v1.

Manifestos antigos param de funcionar quando o cluster é atualizado. kubectl api-resources e api-versions mostram o que o cluster aceita.

Atenção: Antes de um upgrade, procure apiVersions removidas nos seus manifestos e charts. O kubectl avisa ao usar APIs depreciadas.

kubectl api-resources | grep -i ingress
