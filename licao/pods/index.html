Pods e Deployments

A menor peça do Kubernetes, por que ela é descartável e como o cluster mantém cópias sempre vivas.

11 minIniciante12 passos

▶ Abrir a lição interativa

Esta é a versão em texto. A lição interativa tem o diagrama animado de cada passo.

Você vai aprender

  • Saber o que é um pod
  • Saber quando juntar containers no mesmo pod
  • Entender por que pods são descartáveis
  • Usar um Deployment para manter cópias vivas
  • Ver o cluster se recuperar de uma máquina perdida

Passo a passo

Passo 1 · ConceitoO pod: a menor peça do Kubernetes

O Kubernetes não roda containers soltos. Ele embrulha o container num pod, que ganha um endereço IP próprio e é a unidade que o cluster liga, move e desliga.

Pod, em inglês, é a vagem do feijão: uma casquinha com um ou mais grãos dentro. Na maioria dos casos, o pod tem um container só.

Ideia-chave: Container é o programa empacotado. Pod é o apartamento onde ele mora dentro do cluster, com endereço e recursos próprios.

kubectl run api --image=loja/api:1.0

Passo 2 · ConceitoDois containers, um pod

Às vezes dois containers precisam viver colados. Exemplo: a API grava logs num arquivo, e um segundo container lê esse arquivo e envia os logs para um sistema de monitoramento.

Containers do mesmo pod dividem o endereço (falam entre si por localhost) e podem dividir uma pasta, chamada volume. Esse ajudante se chama sidecar, como o carrinho lateral de uma moto.

Passo 3 · ConceitoQuando juntar e quando separar

Regra prática: só coloque dois containers no mesmo pod se eles precisam nascer, crescer e morrer juntos.

O site e o banco de dados não são assim. O site precisa de 3 cópias no pico; o banco, de uma só. Se estivessem no mesmo pod, cada cópia do site levaria um banco junto. Por isso ficam em pods separados.

Bom saber: Na dúvida, separe. Pods separados crescem, são atualizados e falham de forma independente.

Passo 4 · ProblemaPods são descartáveis

O node reiniciou por uma atualização do sistema e o pod da API morreu junto. Ele não volta sozinho: um pod criado à mão não tem ninguém cuidando dele.

O Kubernetes não tenta consertar um pod morto. Ele prefere jogar fora e criar outro.

Atenção: Nunca guarde dados importantes só dentro de um pod. Quando ele some, tudo o que estava lá dentro some junto.

kubectl get pods

Passo 5 · ConceitoGado, não bicho de estimação

Se seu gato fica doente, você leva ao veterinário: ele é único. Num rebanho de mil cabeças, cada animal é tratado como substituível. O Kubernetes trata pods como rebanho.

Um pod substituto nasce com outro nome e outro endereço IP (de 10.1.0.12 para 10.1.0.47). Por isso nada deve depender do endereço de um pod específico.

Ideia-chave: Pods vêm e vão. O que é estável é a descrição do que você quer, não o pod em si.

Passo 6 · SoluçãoDeployment: o pedido por escrito

Em vez de criar pods à mão, você escreve um Deployment: um arquivo YAML (um formato de texto simples) que diz “quero 3 cópias da imagem loja/api:1.0”.

Você envia o arquivo com kubectl apply. O API server confere e anota o pedido no etcd. Nenhum pod existe ainda, mas o desejo está registrado.

Ideia-chave: O Deployment é a receita com quantidade. Ele não é um pod: ele garante que os pods existam.

kubectl apply -f deployment.yaml

Passo 7 · ConceitoAs cópias se espalham

O Deployment cria um ReplicaSet, um contador cuja única tarefa é manter o número certo de cópias. O ReplicaSet cria 3 pods, e o scheduler põe cada um num node diferente.

Espalhar é de propósito: se uma máquina cair, as outras cópias continuam atendendo.

Bom saber: Cópias de um pod se chamam réplicas. Para algo importante, use pelo menos 2; o mais comum é 3.

Passo 8 · ProblemaUm pod falha

Um bug fez a API usar memória demais. O node mata o container para proteger os vizinhos; no painel isso aparece como OOMKilled, “morto por falta de memória”.

O controller do ReplicaSet percebe na hora: o desejado é 3, o real agora é 2.

kubectl get deploy api

Passo 9 · SoluçãoUm substituto nasce sozinho

O ReplicaSet cria um pod novo, o scheduler escolhe um node e, em segundos, o número volta a 3.

Ninguém foi acordado, nenhum script rodou. Isso se chama auto-cura (self-healing).

Ideia-chave: Você nunca diz “reinicie aquele pod”. Você diz “quero 3”, e o sistema persegue esse número.

Passo 10 · ProblemaE se a máquina inteira cair?

O node-3 teve um defeito de hardware e parou de responder. O kubelet dele não manda mais notícias, e o control plane marca o node como NotReady (não pronto).

O Kubernetes espera um pouco, cerca de 5 minutos por padrão, porque pode ser só uma falha rápida de rede. Depois disso, dá os pods daquele node como perdidos.

Atenção: Durante essa espera, o app funciona com uma cópia a menos. É por isso que réplicas extras importam.

Passo 11 · SoluçãoOs pods mudam de casa

O ReplicaSet cria um substituto e o scheduler o coloca num node saudável, o node-1. O estado volta a bater com o desejado.

Quando o node-3 voltar, ele simplesmente recebe pods novos no futuro. Nada precisa ser “devolvido”.

kubectl get pods -o wide

Passo 12 · ResumoResumo: pod, ReplicaSet e Deployment

No dia a dia você só escreve Deployments. ReplicaSets e pods são criados a partir deles.

Bom saber: Bancos de dados e outros apps que guardam dados usam um primo do Deployment, o StatefulSet, que dá nome e disco fixos a cada cópia.
