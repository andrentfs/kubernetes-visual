Segurança e RBAC

Quem pode fazer o quê no cluster: usuários, ServiceAccounts, Roles, ClusterRoles e seus bindings.

Passo a passo

Passo 1 · ContextoNo começo, todo mundo é admin

A loja agora tem duas áreas no cluster, separadas por namespaces: “loja” (o site) e “financeiro” (pagamentos). Namespace é como uma pasta: agrupa os recursos de um time.

Para simplificar, a desenvolvedora Ana e o robô de deploy (ci-bot) receberam cluster-admin: podem ler, mudar e apagar qualquer coisa em qualquer namespace.

Bom saber: Namespaces sozinhos não protegem nada. Eles organizam; quem protege é o RBAC.

kubectl get clusterrolebindings

Passo 2 · ProblemaUm comando no lugar errado

Ana queria limpar pods de teste no namespace dela, mas o terminal estava apontando para “financeiro”. Um kubectl delete pods --all e os pagamentos saíram do ar.

Ninguém agiu de má-fé. O problema foi o acesso: ela podia fazer algo que o trabalho dela nunca exigiu.

Atenção: Permissão demais transforma qualquer erro de digitação, ou senha vazada, num incidente grave.

kubectl delete pods --all -n financeiro

Passo 3 · ConceitoTodo pedido passa por 3 portões

Cada pedido ao API server passa por três etapas, em ordem. Autenticação: quem é você? (certificado, token ou login da empresa via OIDC). Autorização: você pode fazer isso? (é aqui que entra o RBAC).

Admissão: o pedido segue as regras do cluster? Os admission controllers podem recusar (por exemplo, um pod sem limites de recursos) ou ajustar o pedido antes de salvar.

Ideia-chave: Errou no primeiro portão: 401 Unauthorized. Passou no primeiro e barrou no segundo: 403 Forbidden.

Passo 4 · ConceitoQuem pede: usuários, grupos e ServiceAccounts

O Kubernetes não tem cadastro de pessoas. Um usuário (como “ana”) e seus grupos (como “devs”) vêm de fora: do certificado ou do provedor de login.

Já os programas que rodam dentro do cluster usam ServiceAccounts: identidades criadas pelo próprio Kubernetes, uma por namespace ou mais, para robôs e pods.

Bom saber: Esses três são chamados de subjects. Toda permissão no RBAC é dada a um subject.

Passo 5 · ConceitoRole: a lista do que é permitido

Uma Role é uma lista de regras dentro de um namespace. Cada regra diz: quais recursos (pods, services, secrets…) e quais verbos (get, list, watch, create, update, patch, delete).

Aqui, a Role “leitor-pods” no namespace loja permite só get, list e watch em pods. Ela ainda não vale para ninguém: é só a lista.

Ideia-chave: RBAC só soma permissões. Não existe regra de “negar”: o que não está em nenhuma Role é proibido.

kubectl create role leitor-pods --verb=get,list,watch --resource=pods -n loja

Passo 6 · ConceitoRoleBinding: entregar a lista a alguém

Um RoleBinding liga uma Role a um ou mais subjects. É como entregar o crachá certo para a pessoa certa.

O RoleBinding “ana-leitora” diz: a usuária ana recebe a Role leitor-pods no namespace loja. Agora a regra vale.

kubectl create rolebinding ana-leitora --role=leitor-pods --user=ana -n loja

Passo 7 · SoluçãoPode aqui, não pode ali

Ana lista os pods da loja: funciona. Tenta apagar um pod do financeiro: o API server responde 403 Forbidden, e nada acontece.

Para conferir sem arriscar, use kubectl auth can-i. Com --as, um admin testa as permissões de outra pessoa.

Bom saber: O princípio do menor privilégio: cada um recebe só o necessário para o próprio trabalho, e nada além.

kubectl auth can-i delete pods -n financeiro --as ana

Passo 8 · ConceitoClusterRole: regras para o cluster todo

Algumas coisas não ficam em namespace nenhum, como nodes e PersistentVolumes. Outras vezes, alguém precisa ler todos os namespaces. Para isso existe a ClusterRole.

O Prometheus (monitoramento) precisa ler tudo. Uma ClusterRoleBinding liga a ClusterRole “view” à ServiceAccount dele, valendo para o cluster inteiro.

Atenção: ClusterRoleBinding com cluster-admin é a chave-mestra do cluster. Revise quem tem isso, de tempos em tempos.

kubectl create clusterrolebinding monitor-view --clusterrole=view --serviceaccount=monitoring:prometheus

Passo 9 · ConceitoUma ClusterRole, vários namespaces

Um truque útil: um RoleBinding pode apontar para uma ClusterRole. Aí as regras da ClusterRole valem só dentro do namespace daquele RoleBinding.

Assim você escreve a lista uma vez (a ClusterRole “view”) e entrega por namespace, com um RoleBinding em cada um.

Passo 10 · ConceitoPods também têm identidade

Todo pod roda com uma ServiceAccount. Se você não escolher, ele usa a “default” do namespace, que não tem permissões no RBAC.

Quando um app precisa falar com o API server (um operador, uma ferramenta de deploy), crie uma ServiceAccount própria, dê a ela uma Role pequena e indique no pod com serviceAccountName.

Bom saber: Se o pod não fala com o API server, use automountServiceAccountToken: false. Menos credenciais dentro do container, menos risco se ele for invadido.

Passo 11 · Trade-offTrade-off: cuidado com os Secrets

Secrets guardam senhas e chaves. Mas, por padrão, o conteúdo fica só em base64, que é uma codificação e não criptografia: quem lê o Secret lê a senha.

Por isso, permissão de get ou list em secrets equivale a ter as senhas. E quem pode criar pods num namespace consegue montar qualquer Secret de lá dentro de um pod.

Atenção: Ative a criptografia do etcd (encryption at rest), não dê list/get em secrets sem necessidade e lembre que a ClusterRole “view” de propósito não inclui Secrets.

kubectl auth can-i get secrets -n financeiro --as ana

Passo 12 · ResumoResumo: as peças do RBAC

Monte permissões de baixo para cima: o mínimo necessário, por namespace, revisado de tempos em tempos.

Bom saber: No exame: kubectl create role, create rolebinding e auth can-i --as resolvem a maior parte das questões de RBAC sem escrever YAML à mão.
