Passo a passo

Passo 1 · ContextoAlguém abriu um shell no pod

Um invasor conseguiu kubectl exec no pod api e abriu um shell. Dali ele pode ler o token da ServiceAccount, baixar ferramentas e procurar outros alvos.

Nenhum firewall enxerga isso: é só um processo novo dentro de um container que já estava rodando.

kubectl exec -it api -- sh

Passo 2 · ConceitoFalco: olhando as chamadas ao kernel

O Falco roda em cada node (normalmente como DaemonSet) e observa as syscalls de todos os containers com eBPF.

As regras são YAML: condition descreve o evento, output a mensagem e priority a gravidade. Regras próprias vão em /etc/falco/falco_rules.local.yaml (ou na pasta rules.d), sem mexer nas padrão.

Passo 3 · SoluçãoO alerta e a resposta

A regra padrão “Terminal shell in container” dispara e mostra o container, o comando e os dados do pod. Leia o alerta nos logs do Falco: journalctl -u falco, ou kubectl logs no pod do Falco.

Com o ID do container, crictl ps --id <id> e crictl inspect levam ao pod. Na prova costumam pedir para isolar ou remover o pod e anotar a resposta num arquivo.

Atenção: Ajustar a saída de uma regra (por exemplo, incluir %k8s.pod.name) é tarefa comum. Reinicie o Falco depois de editar.

journalctl -u falco --since "10 min ago"

Passo 4 · ConceitoAmeaças em cada camada

O currículo pede detectar ameaças na infraestrutura, nos apps, na rede, nos dados, nos usuários e nas cargas. Cada uma deixa um rastro diferente.

OndeSinal típico
CargaCPU alta sem motivo (minerador)
RedeConexão inesperada para fora
DadosLeitura de /etc/shadow ou de tokens
Usuáriosexec e get secrets fora do normal (audit log)
InfraestruturaPod privilegiado ou com hostPath /

Passo 5 · ConceitoInvestigando as fases do ataque

Ataques seguem fases: acesso inicial, execução, persistência, escalada de privilégios, movimento lateral e roubo de dados. O MITRE ATT&CK e a matriz de ameaças para Kubernetes da Microsoft organizam essas fases.

Para reconstruir o que aconteceu, cruze o alerta do Falco, os logs do container e o audit log do API server.

Ideia-chave: Guarde as evidências antes de apagar o pod: logs, describe e o alerta. Apagado o pod, o container some.

Passo 6 · SoluçãoContainer imutável

Um container imutável não pode ser alterado depois de iniciado: readOnlyRootFilesystem: true, e emptyDir só onde o app precisa escrever (como /tmp).

Junte com runAsNonRoot, allowPrivilegeEscalation: false e uma imagem sem shell. O invasor até entra, mas não grava ferramentas nem muda o app.

kubectl get pod api -o jsonpath='{.spec.containers[*].securityContext}'

Passo 7 · ConceitoAudit log: quem fez o quê

O API server pode registrar cada requisição: quem pediu, o quê, quando e com qual resultado. Uma Policy de auditoria define o nível de cada caso: None, Metadata, Request ou RequestResponse.

As regras são lidas em ordem e vale a primeira que combinar. Para Secrets, use Metadata: registrar o corpo gravaria a senha no log.

Passo 8 · SoluçãoLigando a auditoria

No kube-apiserver: --audit-policy-file=/etc/kubernetes/audit/policy.yaml e --audit-log-path=/var/log/kubernetes/audit/audit.log, mais --audit-log-maxage, --audit-log-maxbackup e --audit-log-maxsize para a rotação.

O pod estático precisa enxergar esses caminhos: adicione volumes hostPath e volumeMounts para a policy e para a pasta do log.

Atenção: Esqueceu o volume? O API server não sobe. Confira com crictl ps -a e com os logs em /var/log/pods.

grep audit /etc/kubernetes/manifests/kube-apiserver.yaml

Passo 9 · ProblemaAchando o responsável

Um Secret foi apagado. Cada linha do audit.log é um JSON: procure verb delete com resource secrets e leia user.username, sourceIPs e requestReceivedTimestamp.

Aqui foi a ServiceAccount ci-bot, que tinha mais permissão do que precisava. A correção vai para o RBAC.

grep '"resource":"secrets"' /var/log/kubernetes/audit/audit.log | grep '"verb":"delete"'

Prevenção nunca é total. Tenha como ver o que acontece dentro dos containers e quem mexeu na API.
