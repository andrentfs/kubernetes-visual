Scheduling: recursos, afinidade e taints

Como decidir onde cada pod roda: reservas de CPU e memória, quotas, rótulos, afinidades, taints e manutenção de nodes.

Passo a passo

Passo 1 · ContextoRelembrando: quem escolhe o node

Todo pod novo sem node passa pelo scheduler. Ele elimina os nodes que não servem e dá nota aos que sobram.

Nesta lição você vai aprender a influenciar essa escolha: dizer quanto o pod precisa, onde ele pode e onde ele não pode rodar.

Passo 2 · ConceitoRequests, limits e QoS

Request é a reserva: o scheduler só põe o pod num node que tenha essa quantia livre. Limit é o teto: passou do limite de CPU, o container fica mais lento (throttling); passou do de memória, é morto (OOMKilled).

Pela combinação, o pod ganha uma classe de QoS: Guaranteed (request igual ao limit), Burstable (só alguns valores) ou BestEffort (nada definido).

Ideia-chave: Quando falta memória no node, o kubelet despeja primeiro os BestEffort, depois os Burstable. Guaranteed são os últimos.

Passo 3 · ProblemaPods sem limites derrubam vizinhos

Um job de relatórios foi criado sem requests nem limits. O scheduler achou que ele não precisava de nada e o pôs no node-2, que já estava cheio.

O job consumiu toda a memória. O kubelet começou a despejar pods (evicted) para salvar o node.

Atenção: Sem requests, o scheduler trabalha às cegas. Sem limits, um pod pode consumir o node inteiro.

Passo 4 · SoluçãoLimitRange e ResourceQuota

LimitRange define valores padrão e máximos por container num namespace. Pods sem requests ganham os padrões automaticamente.

ResourceQuota define o total do namespace: por exemplo, no máximo 4 CPUs reservadas e 10 pods. Pedido acima disso é recusado com “exceeded quota”.

Bom saber: Com uma quota de CPU ou memória ativa, todo pod do namespace precisa declarar requests, senão é recusado. Um LimitRange com padrões evita isso.

kubectl create quota loja --hard=requests.cpu=4,pods=10 -n loja

Passo 5 · ConceitonodeSelector: escolher pelo rótulo

Nodes também têm labels. Você marca o node-2 com disktype=ssd e, no pod, escreve nodeSelector: disktype: ssd.

O scheduler só considera nodes com esse rótulo. Se nenhum tiver, o pod fica Pending.

kubectl label node node-2 disktype=ssd

Passo 6 · ConceitoNode affinity: regras mais ricas

A afinidade de node faz o mesmo que o nodeSelector, com mais opções: operadores como In, NotIn e Exists, e dois níveis.

requiredDuringSchedulingIgnoredDuringExecution é obrigatório. preferredDuringSchedulingIgnoredDuringExecution é preferência com peso: o scheduler tenta, mas usa outro node se precisar.

Bom saber: “IgnoredDuringExecution” quer dizer que, se o rótulo do node mudar depois, o pod que já está rodando não é removido.

Passo 7 · ConceitoAfinidade entre pods

Também dá para decidir em relação a outros pods. podAntiAffinity com topologyKey: kubernetes.io/hostname diz: “não ponha duas réplicas no mesmo node”.

podAffinity faz o contrário: aproxima pods que conversam muito, como o app e o seu cache.

Ideia-chave: Anti-afinidade espalha as réplicas: se um node cair, só uma cópia vai junto.

Passo 8 · ConceitoTaints e tolerations: a placa de “proibido entrar”

Um taint é uma marca no node que repele pods. kubectl taint nodes node-3 gpu=true:NoSchedule faz o scheduler evitar o node-3.

Só entram pods com uma toleration que combine com o taint. É assim que nodes caros, como os de GPU, ficam reservados.

EfeitoO que faz
NoScheduleNão agenda pods novos
PreferNoScheduleEvita, se der
NoExecuteTambém expulsa os que estão lá
kubectl taint nodes node-3 gpu=true:NoSchedule

Passo 9 · Trade-offTrade-off: tolerar não é ser atraído

O pod de machine learning tem a toleration, mas o scheduler o pôs no node-2. A toleration só permite entrar no node com taint; não obriga.

Para garantir que ele vá para o node de GPU, combine a toleration com node affinity (ou nodeSelector) apontando para aquele node.

Atenção: Taint afasta os outros. Afinidade atrai o certo. Para reservar um node, use os dois.

Passo 10 · ConceitoManutenção: cordon e drain

kubectl cordon node-2 marca o node como SchedulingDisabled: nada novo entra, e o que está lá continua.

kubectl drain node-2 faz o cordon e ainda tira os pods de lá com segurança, para serem recriados em outros nodes. Depois da manutenção, kubectl uncordon libera de novo.

Atenção: O drain para em pods de DaemonSet e em pods com emptyDir. Use --ignore-daemonsets e --delete-emptydir-data, entendendo o que cada um faz.

kubectl drain node-2 --ignore-daemonsets --delete-emptydir-data

Passo 11 · ConceitoStatic pods e nodeName

Os componentes do control plane (etcd, API server, scheduler) são static pods: arquivos YAML em /etc/kubernetes/manifests que o kubelet liga sozinho, sem passar pelo scheduler.

E nodeName no pod pula o scheduler: o pod vai direto para o node indicado. Útil quando o scheduler está fora do ar.

Ideia-chave: Static pod aparece no kubectl com o nome do node no fim (como etcd-controlplane). Para mudar, edite o arquivo; apagar pelo kubectl não adianta.

Passo 12 · ResumoResumo: como influenciar o scheduler

Recursos dizem quanto, rótulos e afinidades dizem onde, taints dizem onde não.

RecursoEfeito
requests/limitsReserva e teto por container
LimitRange/QuotaPadrões e totais por namespace
nodeSelector/affinityAtrai para certos nodes
taint/tolerationAfasta de certos nodes
cordon/drainTira o node de uso
