Service e Ingress

Pods mudam de endereço o tempo todo. Como o site acha a API, e como a internet acha a loja?

11 minIniciante11 passos

▶ Abrir a lição interativa

Esta é a versão em texto. A lição interativa tem o diagrama animado de cada passo.

Você vai aprender

  • Entender por que não se usa o endereço de um pod
  • Usar um Service como nome fixo
  • Ver o Service desviar de pods doentes
  • Abrir o app para a internet com um Ingress

Passo a passo

Passo 1 · ContextoO site conversa com a API

Quando alguém abre a loja, o pod do site (web) pede à API a lista de produtos e os preços. Hoje existem 3 pods da API espalhados pelos nodes.

Por enquanto, o site foi configurado com o endereço IP de cada pod da API, anotado à mão.

Passo 2 · ProblemaOs endereços mudam

Um pod da API foi recriado e ganhou endereço novo: era 10.1.2.7, agora é 10.1.2.9. O site continua ligando para o número antigo, e as requisições se perdem.

Lembra da lição anterior? Pods são descartáveis. Qualquer coisa que dependa do IP de um pod quebra na primeira troca.

Atenção: Anotar IPs de pods é como anotar o ramal de um funcionário temporário: na semana seguinte, outra pessoa atende, ou ninguém atende.

Passo 3 · SoluçãoService: um nome que não muda

Um Service dá aos pods um nome fixo, como “api”, e um endereço que nunca muda. O site passa a chamar http://api e não precisa saber quais pods existem por trás.

É como o número da central de atendimento: você liga sempre para o mesmo número, e a central passa para quem estiver livre.

Ideia-chave: O Service é estável; os pods atrás dele mudam o tempo todo. Quem chama o Service nem percebe.

kubectl expose deployment api --port=80

Passo 4 · ConceitoEtiquetas: como o Service acha os pods

Cada pod tem etiquetas chamadas labels, como app=api ou app=web. O Service tem um filtro, o selector, que diz: “quero todos os pods com app=api”.

Pod novo com a etiqueta certa entra sozinho na lista. Pod que morre sai sozinho. Essa lista fica em objetos EndpointSlice (o objeto antigo, Endpoints, está deprecated desde a v1.33).

Bom saber: Labels são a cola do Kubernetes: Services, Deployments e várias ferramentas encontram as coisas por etiqueta, não por nome.

Passo 5 · ConceitoO Service divide o trabalho

Cada requisição para http://api vai para um dos pods da lista. Na média, cada pod recebe um terço do trabalho, e todos ficam com a CPU parecida, perto de 34%.

Isso se chama balanceamento de carga: espalhar as requisições para ninguém ficar sobrecarregado enquanto outro fica parado.

Passo 6 · ProblemaUm pod adoece

Um dos pods perdeu a conexão com o banco. Ele está ligado, mas responde com erro. O kubelet faz um health check chamado readiness probe (“você está pronto para atender?”) e recebe um não.

Enquanto isso, algumas requisições ainda caem nesse pod e falham.

Atenção: Pod ligado não é o mesmo que pod saudável. Sem a readiness probe, o Kubernetes não tem como saber a diferença.

Passo 7 · SoluçãoDoente sai da lista na hora

Assim que a readiness probe falha, o pod é tirado dos endpoints do Service. Ninguém mais manda requisições para ele.

Os outros dois pods assumem o trabalho (a CPU sobe para 50%). Quando o pod doente se recuperar e passar na probe, volta para a lista sozinho.

kubectl get endpointslices -l kubernetes.io/service-name=api

Passo 8 · ProblemaE quem está fora do cluster?

O Service que criamos é do tipo ClusterIP: o endereço só funciona dentro do cluster. Para seus clientes, que estão na internet, a loja simplesmente não existe.

Precisamos de uma porta de entrada pública.

Passo 9 · SoluçãoIngress: a portaria do prédio

Um Ingress é a portaria do cluster. Ele recebe o tráfego da internet num endereço público e encaminha para o Service certo.

Por trás dele roda um programa chamado Ingress Controller, como o NGINX ou o Traefik, que faz o trabalho de verdade.

Bom saber: O Kubernetes está trocando o Ingress pelo Gateway API, mais moderno e flexível. A ideia é a mesma: uma porta de entrada com regras.

kubectl get ingress

Passo 10 · ConceitoUm endereço, vários destinos

A portaria lê o endereço de cada visita e decide para onde mandar: loja.com/ vai para o Service web (as páginas); loja.com/api vai para o Service api (os dados).

Ela também cuida do cadeado do navegador, o certificado HTTPS que deixa a conexão criptografada.

Ideia-chave: Um único endereço público atende o site inteiro. Para criar uma área nova, basta uma regra nova no Ingress.

Passo 11 · ResumoResumo: formas de expor um app

Na prática: ClusterIP para conversas internas e Ingress para o que vem da internet.
