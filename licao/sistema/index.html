Hardening do sistema: host, portas, AppArmor e seccomp

O node é um Linux como outro qualquer. Menos pacotes, menos portas e menos privilégios, mais perfis do kernel que limitam o que um container pode fazer.

Você vai aprender

  • Reduzir pacotes, serviços e portas do node
  • Saber quais portas o Kubernetes usa
  • Fechar o resto com firewall
  • Aplicar identidade com mínimo privilégio
  • Usar AppArmor e seccomp nos pods

Passo a passo

Passo 1 · ContextoO que roda no node

Além do kubelet e do containerd, o node-1 tem o sshd, um apache2 esquecido de um teste e o cups (impressão). Cada serviço é uma porta aberta e mais um programa que pode ter falhas.

ss -tlnp lista as portas TCP em escuta e o processo de cada uma.

ss -tlnp

Passo 2 · SoluçãoRemovendo o que não precisa

systemctl disable --now para o serviço e o tira do boot. Se o pacote não é usado, remova com apt remove (ou o gerenciador da sua distribuição).

Faça o mesmo com usuários, compiladores e ferramentas que só ajudariam um invasor.

systemctl disable --now apache2 cups

Passo 3 · ConceitoAs portas que o Kubernetes usa

No control plane: 6443 (API server), 2379-2380 (etcd), 10250 (kubelet), 10259 (scheduler) e 10257 (controller-manager). Nos workers: 10250 (kubelet) e a faixa de NodePort, 30000-32767.

O CNI pode precisar de outras portas; confira na documentação dele.

Passo 4 · SoluçãoFechando o resto no firewall

Com o ufw: ufw default deny incoming e depois ufw allow 6443/tcp (e as outras portas que o node precisa). Na nuvem, faça o mesmo no security group.

O etcd só deve ser acessível pelo API server, nunca de fora.

Atenção: Antes do ufw enable, libere a porta 22 se estiver conectado por SSH, ou você perde o acesso.

ufw default deny incoming

Passo 5 · ConceitoIdentidade e acesso com mínimo privilégio

No node: só os usuários necessários, SSH só com chave e sudo apenas para quem administra. id ana mostra os grupos de um usuário.

Na nuvem: o papel (IAM role) da máquina deve ter só as permissões que o kubelet e os agentes usam. No cluster, o mesmo vale para o RBAC.

Ideia-chave: Um invasor que chega ao node herda tudo o que o node pode fazer, inclusive na conta da nuvem.

id ana

Passo 6 · ConceitoAppArmor: limitando o que o processo acessa

O AppArmor é um módulo de segurança do kernel. Um perfil diz quais arquivos, capacidades e acessos de rede um programa pode usar.

O perfil é carregado no node (apparmor_parser -q arquivo), e aa-status lista os carregados. O Kubernetes não carrega perfis: isso é feito em cada node.

aa-status

Passo 7 · SoluçãoAplicando o perfil ao pod

No securityContext do pod ou do container: appArmorProfile com type: Localhost e localhostProfile: k8s-deny-write. Também existem os tipos RuntimeDefault e Unconfined.

Com um perfil que nega escrita, kubectl exec web -- touch /tmp/x falha com Permission denied: quem bloqueou foi o kernel.

kubectl exec web -- touch /tmp/x

Passo 8 · Trade-offTrade-off: o perfil precisa estar em todo node

O pod web-2 caiu no worker-2, onde o perfil não foi carregado. O kubelet recusa iniciar o pod, e kubectl describe mostra o erro de AppArmor.

Carregue o perfil em todos os nodes que podem receber o pod, ou prenda o pod aos nodes certos com nodeSelector ou afinidade.

Atenção: Perfil carregado à mão some no reboot se o arquivo não estiver em /etc/apparmor.d.

kubectl describe pod web-2

Passo 9 · Conceitoseccomp: filtrando chamadas ao kernel

O seccomp limita quais chamadas de sistema (syscalls) um container pode fazer. seccompProfile com type: RuntimeDefault usa o perfil padrão do container runtime, que bloqueia chamadas perigosas e raras.

Para um perfil próprio, use type: Localhost e localhostProfile com o caminho de um arquivo dentro de /var/lib/kubelet/seccomp no node.

Bom saber: RuntimeDefault é exigido pelo Pod Security Standard restricted. É a escolha segura para quase todo app.

Passo 10 · ResumoResumo: um node com menos superfície

Tire do node o que não é usado, feche as portas que sobram e limite cada container com AppArmor e seccomp.
