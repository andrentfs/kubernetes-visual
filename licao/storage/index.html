Storage: volumes, PV, PVC e StorageClass

Containers esquecem tudo ao reiniciar. Como guardar dados que sobrevivem a pods, reinícios e trocas de máquina.

Esta é a versão em texto. A lição interativa tem o diagrama animado de cada passo.

Você vai aprender

  • Entender por que o disco do container é temporário
  • Conhecer emptyDir e hostPath
  • Separar PersistentVolume de PersistentVolumeClaim
  • Conhecer os modos de acesso
  • Usar StorageClass para criar discos sozinho
  • Cuidar da política de retenção

Passo a passo

Passo 1 · ProblemaO banco perdeu tudo

O pod do banco de dados guardava os dados dentro do próprio container. O pod morreu, um novo nasceu, e o banco começou vazio.

O sistema de arquivos de um container dura só enquanto o container existe. É como escrever num quadro branco que é apagado a cada reinício.

Atenção: Nunca guarde dados importantes no disco do container. Ele é descartável, assim como o pod.

Passo 2 · ConceitoemptyDir e hostPath: os volumes simples

Um volume emptyDir nasce vazio junto com o pod e dura enquanto o pod existir. Serve para cache ou para dois containers do mesmo pod trocarem arquivos. Sobrevive a reinícios do container, mas não à morte do pod.

Um volume hostPath usa uma pasta do próprio node, como /data. Os dados ficam na máquina, mesmo se o pod morrer.

Bom saber: emptyDir pode até ficar na memória (medium: Memory), útil para arquivos temporários rápidos.

Passo 3 · ProblemaO problema do hostPath

O pod do banco foi reagendado no node-2. Os dados continuam na pasta /data do node-1, e o pod novo começa vazio de novo.

Além disso, acessar pastas do node é um risco de segurança. hostPath é para casos de sistema (agentes de log, por exemplo), não para dados de aplicação.

Atenção: Dado de aplicação precisa de um disco que siga o pod para onde ele for.

Passo 4 · ConceitoPersistentVolume: um disco do cluster

Um PersistentVolume (PV) representa um pedaço de armazenamento de verdade: um disco da nuvem, uma pasta NFS, um volume de storage. Ele existe por conta própria, fora de qualquer pod.

O PV não pertence a namespace nenhum. Ele tem um tamanho (como 10Gi), modos de acesso e uma política de retenção.

Ideia-chave: PV é o lado de quem administra o cluster: “este disco existe e está disponível”.

kubectl get pv

Passo 5 · ConceitoPersistentVolumeClaim: o pedido do app

O app não escolhe um disco específico. Ele faz um pedido, o PersistentVolumeClaim (PVC): “quero 5Gi, para um node por vez”.

O Kubernetes procura um PV livre que atenda ao pedido e liga os dois. A partir daí, ambos ficam com status Bound: aquele PV é só daquele PVC.

Bom saber: O PVC fica num namespace, junto com o app. O PV fica no cluster. Separar os dois deixa o time do app pedir disco sem saber detalhes da infraestrutura.

kubectl get pvc

Passo 6 · SoluçãoO pod usa o PVC

No pod, o volume aponta para o PVC: persistentVolumeClaim.claimName: dados, montado em /var/lib/postgresql/data.

Se o pod morrer e outro nascer, mesmo em outro node, ele monta o mesmo PVC e encontra os dados lá.

Ideia-chave: Pod → PVC → PV → disco real. O pod só conhece o PVC.

Passo 7 · ConceitoModos de acesso

Um disco de nuvem comum só pode ser montado por um node por vez: modo ReadWriteOnce (RWO). Se um segundo pod tentar usar em outro node, fica esperando.

Para vários nodes ao mesmo tempo, é preciso um storage de rede que suporte isso, como NFS, com ReadWriteMany (RWX).

Passo 8 · ConceitoStorageClass: discos sob demanda

Criar PVs à mão não escala. Uma StorageClass descreve um tipo de disco (por exemplo, SSD da nuvem) e qual provisioner, geralmente um driver CSI, sabe criá-lo.

Quando um PVC pede storageClassName: rapido, o provisioner cria o disco e o PV automaticamente. Isso é provisionamento dinâmico.

Bom saber: Uma StorageClass pode ser a padrão do cluster. PVCs sem storageClassName usam a padrão.

kubectl get storageclass

Passo 9 · ConceitoWaitForFirstConsumer: criar o disco no lugar certo

Discos de nuvem moram numa zona. Se o disco nascer na zona A e o pod for para a zona B, o pod não consegue montá-lo.

Com volumeBindingMode: WaitForFirstConsumer, o PVC fica Pending até um pod usá-lo. Aí o scheduler escolhe o node primeiro e o disco é criado na zona desse node.

Atenção: PVC em Pending com essa opção é normal até existir um pod. Não confunda com erro.

Passo 10 · Trade-offTrade-off: apagou o PVC, apagou os dados?

A política de retenção do PV decide. Com Delete, padrão no provisionamento dinâmico, apagar o PVC apaga o PV e o disco real. Os dados se vão.

Com Retain, o PV fica com status Released e o disco continua lá. Um administrador recupera os dados ou limpa à mão antes de reutilizar.

Atenção: Para dados importantes, use Retain na StorageClass ou mude o PV existente com kubectl patch antes de qualquer limpeza.

kubectl patch pv pv-dados -p '{"spec":{"persistentVolumeReclaimPolicy":"Retain"}}'

Passo 11 · ConceitoAumentar um volume

O banco cresceu. Se a StorageClass tiver allowVolumeExpansion: true, basta editar o PVC e trocar 10Gi por 20Gi.

O driver aumenta o disco. Diminuir não é possível: só dá para crescer.

kubectl edit pvc dados

Passo 12 · ResumoResumo: o caminho dos dados

Pod pede ao PVC, o PVC se liga a um PV, e o PV aponta para o disco real, criado à mão ou por uma StorageClass.
