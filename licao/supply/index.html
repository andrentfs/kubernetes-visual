Passo a passo

Passo 1 · ContextoDo git ao pod

O código vai para o git, o CI constrói a imagem, a imagem vai para o registry e o cluster a baixa. Um invasor pode entrar em qualquer elo: uma dependência maliciosa, um CI comprometido, uma imagem trocada no registry.

Supply Chain Security vale 20% da CKS.

Passo 2 · ConceitoImagem base mínima

Quanto menos coisa na imagem, menos vulnerabilidades e menos ferramentas para um invasor. Use build multi-stage: compile numa imagem completa e copie só o resultado para uma base distroless ou alpine.

No Dockerfile, use USER com um usuário sem privilégios e fixe a versão da base, nunca latest.

Bom saber: Imagens distroless não têm shell nem gerenciador de pacotes. Quem entra no container fica sem ferramentas.

podman build -t loja/api:v2 .

Passo 3 · ProblemaEscaneando vulnerabilidades

O Trivy compara os pacotes da imagem com bancos de vulnerabilidades conhecidas (CVEs). trivy image --severity HIGH,CRITICAL loja/api:v2 mostra só as graves.

A saída lista o pacote, a CVE, a versão instalada e a versão que corrige.

trivy image --severity HIGH,CRITICAL loja/api:v2

Passo 4 · SoluçãoCorrigindo e escaneando de novo

Atualize a imagem base ou o pacote para a versão corrigida, reconstrua e escaneie de novo. Só então faça o deploy.

No CI, o Trivy pode falhar o build quando acha algo grave: --exit-code 1 junto com --severity CRITICAL.

trivy image --severity HIGH,CRITICAL loja/api:v3

Passo 5 · ConceitoSBOM: a lista de ingredientes

Um SBOM (Software Bill of Materials) lista todos os componentes de uma imagem: pacotes, bibliotecas e versões. Os formatos mais comuns são CycloneDX e SPDX.

trivy image --format cyclonedx --output sbom.json loja/api:v3 gera o SBOM. Quando sai uma CVE nova, trivy sbom sbom.json diz se a imagem é afetada, sem baixá-la de novo.

trivy image --format cyclonedx --output sbom.json loja/api:v3

Passo 6 · ConceitoAnálise estática dos manifestos

Antes do apply, ferramentas leem o YAML e apontam riscos: privileged, rodar como root, sem limites, hostPath.

kubesec scan pod.yaml devolve uma nota e sugestões. kube-linter lint pod.yaml lista os problemas por regra. As duas cabem no CI.

kubesec scan pod.yaml

Passo 7 · SoluçãoAssinando e verificando imagens

Com o cosign, o CI assina a imagem depois do build: cosign sign --key cosign.key registry.loja.com/api@sha256:<digest>. A assinatura fica no próprio registry.

Antes do deploy: cosign verify --key cosign.pub registry.loja.com/api:v3. Imagem trocada ou sem assinatura falha na verificação.

cosign verify --key cosign.pub registry.loja.com/api:v3

Passo 8 · SoluçãoSó registries permitidos

Um admission controller recusa pods com imagens de fora. Com uma ValidatingAdmissionPolicy (mais o seu binding), a regra em CEL pode ser object.spec.containers.all(c, c.image.startsWith('registry.loja.com/')).

Outra opção, comum na prova, é o ImagePolicyWebhook: o kube-apiserver consulta um serviço externo antes de aceitar cada imagem, configurado por --admission-control-config-file.

Atenção: No ImagePolicyWebhook, defaultAllow: false recusa tudo quando o serviço externo não responde. Confira o que a tarefa pede.

kubectl run x --image=docker.io/evil/miner

Passo 9 · Trade-offTrade-off: tag ou digest

Uma tag (api:v3) pode ser movida para outra imagem no registry. O digest (api@sha256:…) identifica exatamente um conteúdo e não muda.

Fixar o digest garante que roda o que foi escaneado e assinado, mas cada atualização exige trocar o digest no manifesto, de preferência pelo CI.

kubectl set image deploy/api api=registry.loja.com/api@sha256:<digest>
