Troubleshooting de cluster

O domínio que mais pesa na CKA: achar o problema com método, do pod ao node e ao control plane.

Você vai aprender

Passo a passo

Passo 1 · ContextoUm roteiro para qualquer problema

Na hora do aperto, siga sempre a mesma ordem: kubectl get para ver o estado, describe para ler os eventos, logs para ver o que o app disse.

Se o problema for o próprio cluster, desça um nível: o node (kubelet, runtime) e, por último, os componentes do control plane.

Ideia-chave: O STATUS do pod já diz por onde começar: Pending é agendamento, ImagePullBackOff é imagem, CrashLoopBackOff é o app ou a config.

kubectl get pods -A | grep -v Running

Passo 2 · ProblemaImagePullBackOff: a imagem não veio

O node não conseguiu baixar a imagem. O describe mostra o motivo nos eventos: nome ou tag errados (nginx:1.2O, com a letra O), registry privado sem login ou registry fora do ar.

Corrija a imagem no Deployment (kubectl set image) ou crie o Secret de registry e coloque em imagePullSecrets.

Atenção: Olhe a seção Events do describe. A mensagem exata (not found, unauthorized) já mostra a causa.

kubectl describe pod web

Passo 3 · ProblemaPending: ninguém aceitou o pod

Pod em Pending não foi agendado. O describe mostra FailedScheduling e o motivo: Insufficient cpu ou memory, node com taint sem toleration, nodeSelector que nenhum node atende ou PVC que não fez bind.

A solução depende do motivo: reduzir requests, liberar espaço, corrigir o rótulo ou a toleration, ou arrumar o PVC.

Bom saber: “0/3 nodes are available: 3 Insufficient cpu” significa que os 3 nodes foram descartados pelo mesmo motivo.

Passo 4 · ProblemaCrashLoopBackOff: o app liga e morre

O container sobe e sai logo em seguida, várias vezes. O log de agora pode estar vazio; use kubectl logs --previous para ver a execução que caiu.

O código de saída no describe ajuda: 137 é morto por falta de memória (OOMKilled) ou por um kill; 1 costuma ser erro do app; comando ou argumento errado também aparece aqui.

Exit codeCausa comum
0O comando terminou (falta loop?)
1Erro da aplicação
127Comando não encontrado
137Morto: OOM ou kill
kubectl logs api-7d9 --previous

Passo 5 · ProblemaService sem endpoints

Os pods estão Running, mas ninguém consegue acessar o Service. kubectl get endpointslices -l kubernetes.io/service-name=web mostra a coluna ENDPOINTS vazia (<unset>).

Quase sempre é o selector: o Service procura app=wbe e os pods têm app=web. Também confira targetPort (a porta do container) e se os pods passam na readiness.

Atenção: Compare kubectl describe svc (Selector, TargetPort) com kubectl get pods --show-labels.

kubectl get endpointslices -l kubernetes.io/service-name=web

Passo 6 · ProblemaNode NotReady

O node-3 aparece NotReady em kubectl get nodes. Sem notícias do kubelet, o control plane para de mandar pods para lá.

Entre no node (ssh) e verifique o kubelet: systemctl status kubelet. Ele pode estar parado, sem conseguir falar com o runtime, ou com a configuração errada.

Atenção: No exame é comum o kubelet estar parado ou desabilitado de propósito. systemctl enable --now kubelet resolve os dois.

kubectl describe node node-3

Passo 7 · SoluçãoLendo o kubelet

journalctl -u kubelet mostra o porquê: caminho errado de certificado, arquivo de config com erro, porta do runtime errada.

A configuração fica em /var/lib/kubelet/config.yaml, e as credenciais para falar com o API server em /etc/kubernetes/kubelet.conf. Corrija, reinicie e confira o node voltando a Ready.

systemctl restart kubelet

Passo 8 · ProblemaO API server caiu

kubectl responde “connection refused” na porta 6443. Sem o API server, o kubectl não funciona, então não dá para usar kubectl describe para investigar.

Isso costuma vir de um erro no manifesto do static pod /etc/kubernetes/manifests/kube-apiserver.yaml: um flag errado, um caminho de certificado que não existe.

Atenção: O kubelet recria o static pod a cada mudança no arquivo. Um erro de digitação ali derruba o API server na hora.

Passo 9 · Soluçãocrictl: olhar os containers sem o kubectl

Sem API server, você vai direto ao runtime do node. crictl ps -a lista todos os containers, inclusive os que caíram; crictl logs <id> mostra o erro.

Os logs também ficam em /var/log/pods e /var/log/containers. Corrija o manifesto e espere o kubelet religar o static pod.

Bom saber: Ao editar um manifesto, salve uma cópia antes fora da pasta manifests. Arquivos .yaml extras dentro dela também viram pods.

crictl ps -a | grep kube-apiserver

Passo 10 · ProblemaScheduler ou controller-manager fora

Se todo pod novo fica Pending sem nenhum evento de agendamento, o scheduler está fora. Se você escala um Deployment e nada acontece, desconfie do controller-manager.

Os dois também são static pods. Veja kubectl get pods -n kube-system e os logs deles, e corrija o manifesto.

Ideia-chave: Pending sem evento FailedScheduling = ninguém tentou agendar. Isso aponta para o scheduler, não para os nodes.
