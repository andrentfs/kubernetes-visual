Passo a passo

Passo 1 · ContextoDeployment: para apps sem estado

O Deployment é perfeito para apps sem estado, como a API da loja: as réplicas são iguais e qualquer uma pode ser trocada por outra.

Mas há casos em que isso não serve: um agente que precisa rodar em toda máquina, um banco em que cada réplica é diferente, uma tarefa que deve terminar.

Passo 2 · ConceitoDaemonSet: um pod em cada node

Um DaemonSet garante exatamente um pod em cada node (ou em cada node que combine com um seletor). Entrou um node novo, ele já recebe o seu pod.

É o jeito certo para agentes de log (Fluent Bit), monitoramento (node-exporter) e rede (o próprio CNI e o kube-proxy).

Bom saber: DaemonSets ignoram o número de réplicas: quem decide quantos pods existem é a quantidade de nodes.

kubectl get ds -A

Passo 3 · ConceitoStatefulSet: cada réplica é única

Bancos de dados precisam que cada réplica tenha identidade fixa. O StatefulSet cria pods com nomes estáveis (db-0, db-1, db-2) e, com volumeClaimTemplates, um PVC próprio para cada um.

Se db-1 morrer, nasce outro db-1, que monta o mesmo disco data-db-1. Um Service headless dá o endereço db-1.db de cada réplica.

Ideia-chave: Deployment: réplicas trocáveis. StatefulSet: réplicas com nome, ordem e disco próprios.

Passo 4 · ConceitoStatefulSet sobe em ordem

Por padrão, o StatefulSet liga db-0, espera ficar pronto, depois db-1, e só então db-2. Para desligar ou escalar para baixo, faz o caminho inverso.

Isso permite que o banco eleja o primário antes de as réplicas entrarem.

Passo 5 · ConceitoJob: uma tarefa que termina

Um Job roda pods até completar a tarefa e para. completions diz quantas vezes precisa dar certo; parallelism, quantos rodam ao mesmo tempo.

Pod de Job usa restartPolicy Never ou OnFailure. Ao terminar, fica com status Completed para você ler os logs.

kubectl create job relatorio --image=busybox -- sh -c "echo ok"

Passo 6 · ProblemaQuando o Job falha

Se os pods falham, o Job tenta de novo, esperando cada vez mais. Depois de backoffLimit tentativas (padrão 6), desiste e marca o Job como Failed.

activeDeadlineSeconds limita o tempo total, e ttlSecondsAfterFinished apaga o Job sozinho depois de um tempo.

Atenção: Sem backoffLimit ou prazo, um Job com bug pode ficar criando pods por muito tempo.

Passo 7 · ConceitoCronJob: tarefa com horário

Um CronJob cria um Job novo em cada horário marcado. O formato é o do cron do Linux: "0 3 * * *" é todo dia às 3 da manhã.

concurrencyPolicy define o que fazer se a execução anterior ainda não terminou: permitir (Allow), pular (Forbid) ou trocar (Replace).

ExpressãoQuando
*/5 * * * *A cada 5 minutos
0 3 * * *Todo dia às 3h
0 0 * * 0Domingo à meia-noite
kubectl create cronjob backup --image=busybox --schedule="0 3 * * *" -- sh -c "date"

Passo 8 · ConceitoInit containers: preparar antes de ligar

Init containers rodam antes do container principal, um de cada vez, e precisam terminar com sucesso. Só então o app liga.

Usos típicos: esperar o banco responder, baixar uma configuração, ajustar permissões de um volume.

Atenção: Pod preso em Init:0/1? O init container não terminou. Veja o log dele com kubectl logs pod -c nome-do-init.

Passo 9 · ConceitoSidecars e outros padrões

Um sidecar roda ao lado do app no mesmo pod: um proxy, um coletor de logs. No formato nativo, ele é declarado em initContainers com restartPolicy: Always: liga antes do app e fica rodando junto.

Outros padrões: adapter (traduz a saída do app para outro formato) e ambassador (um proxy local para serviços de fora).

Passo 10 · ConceitoBlue/green: trocar tudo de uma vez

Você roda dois Deployments completos: o azul (v1, em produção) e o verde (v2, novo). O Service aponta para um deles pelo label version.

Quando o verde estiver testado, muda o selector do Service para version=v2. A troca é instantânea, e voltar é só mudar o selector de novo.

Bom saber: Custa o dobro de pods durante a troca, mas o rollback leva um segundo.

kubectl patch svc loja -p '{"spec":{"selector":{"version":"v2"}}}'

Passo 11 · ConceitoCanary: testar com poucos clientes

Dois Deployments com o mesmo label app=loja: três pods v1 e um pod v2. O Service manda tráfego para os quatro, então mais ou menos 25% dos clientes usam a versão nova.

Se tudo correr bem, aumente as réplicas da v2 e diminua as da v1 até a troca completa.

Bom saber: Para porcentagens exatas sem mexer em réplicas, a Gateway API permite pesos nas rotas.

Passo 12 · ResumoResumo: qual workload usar

Escolha pela natureza do trabalho, não pelo hábito.
